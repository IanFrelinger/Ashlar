# Changelog

All notable changes to Ashlar are documented in this file.

The format is based on [Keep a Changelog](https://keepachangelog.com/en/1.1.0/), and the project adheres to [Semantic Versioning](https://semver.org/spec/v2.0.0.html). Commit messages follow Conventional Commits by convention (no commitlint hook or workflow enforces it); `scripts/changelog-snippet-for-release.sh` drafts release notes from the commits since the last `v*` tag.

At release time, move the `[Unreleased]` notes under a new `[X.Y.Z] - YYYY-MM-DD` heading, bump `VERSION`, tag `vX.Y.Z`, and publish a GitHub Release.

- **Two more places where reflection-based serialization was fail-OPEN, both on the certification path, both now refusals.** #584 and #589 fixed the signing payload; these are the input-hash and determinism producers beside it, and they degrade the same way. Reflection-based serialization does not fail loudly under a trimmed or ahead-of-time publish — it can return an empty or short payload with no exception, or throw `NotSupportedException` when it is disabled outright. **(1) `CertificationGate.BuildInputs` caught that exception, logged a warning, and minted the certificate with NO WITNESS INPUT AT ALL.** The witness input is the record of what was judged; neither `Default` nor `Strict` requires it (they require `gate-emitted-artifact` and `certifier-identity`), so such a record verifies cleanly downstream and no consumer can tell it binds nothing about the specification it was judged against. The trigger is publish mode alone. It now refuses at mint time with a `CanonicalOutputException` carrying the serializer failure, the precedent #584 set for bytes nobody can vouch for. **(2) `BrickOutputSerializer.ToCanonicalJson` feeds an EQUALITY comparison** — the determinism leg runs a brick twice and compares the two strings — so two *different* outputs that both degrade to `{}` compare equal, the leg reports deterministic, and the certificate records a check that never ran. `BrickOutput` holds arbitrary `object` values set by brick code, so there is no closed type set a source generator could cover and reflection cannot be removed; instead the payload's SHAPE is established before the bytes are returned. The invariant is the top-level property count, which is value-independent and fixed by the dictionary handed to the serializer, re-read with `JsonDocument` — reflection-free, so it still works in exactly the configurations where the serializer does not. `CanonicalOutputShapeGuardTests` pins both, including a positive control and a case proving two different outputs do not serialize alike; the guard is exercised directly against payloads a test host cannot make the serializer emit, the same shape `CanonicalPayloadGuardTests` uses and for the same reason. **Still open:** `SessionEnvironmentInputs` serializes `SandboxSpec` and `SessionAttestation` by reflection for its sandbox-spec and attestation input hashes; those are fixed types, so a source-generated context would make them trim-safe, and that is a separate change.
- **`docs/EmbeddingVersionStamp.md`** — a design, not an implementation, for stamping a stored embedding with the generator that produced it. It is the item #582 deferred in writing ("If a persistent store is ever wired up for real, a version column is the right thing to add then, alongside a migration"), so the document has to say what changed; three things did, and the sharpest is that the generator #582 named is not the one that ships. `AshlarKernelRegistrar` phase 13b overrides `IRAGService` unconditionally, so both hosts search `InProcessChunkCollection` through a **Microsoft** `IEmbeddingGenerator` that Ashlar cannot add a member to, behind two `DelegatingEmbeddingGenerator` decorators that do not forward `GetService` — a design that only moves Ashlar's own interface leaves the live generator unstamped. It settles the migration in detail, because that is the part that is cheap on paper and expensive in a released schema: `rag_vectors` is created with `CREATE TABLE IF NOT EXISTS` and there is no migration mechanism anywhere in the assembly, so adding a column to the statement is a silent no-op on an existing file and the reader then throws "no such column" at search time; and SQLite rejects `ALTER TABLE ADD COLUMN` with `NOT NULL` and no default on a non-empty table. It also records two things found while checking premises rather than trusting them: `RAGConfig.VectorStoreProvider` is validated non-empty and then never read to select a store, so a config declaring `"sqlite"` is accepted and silently served an in-memory one; and `src/Ashlar.AI.Pipeline/` is in neither of the readiness gate's two path lists, so a change to the generator that is live in every host fires no lane that runs its tests.
- **`UnstableHashKeyConventionTests`** — the frozen inventory of every production `.GetHashCode()` call that is not implementing an equality contract, in the namespace `cert-gate` runs, so a seventh site has to be argued for in a diff a reviewer sees. `string.GetHashCode()` is randomized per process, and the resulting failure is always silent: a cache that never hits looks exactly like a cache that is cold. Six such call sites had accumulated across five files in four assemblies with nothing to slow them down — nothing in `.editorconfig`, `scripts/`, or any workflow bans the shape, and #582's golden constants protect its two generators and nothing else. Three rows remain, each carrying a written verdict on the member itself saying why in-process is sufficient there and exactly what would overturn it: the synthesis cache (an `AddSingleton` registration a consumer can replace with a Redis-backed one, and a 24-hour TTL that already assumes a durability the in-memory store cannot provide); the schema grouping (a dictionary local to one method — where a stable hash is *not* what is wrong, since the hash branch is nearly dead and the key is taken over raw text, so two spellings of one schema already split); and the composition cache (where the real bug is that the derivation is not on the port, so no caller can construct a key that hits). Three facts, not two: a new offender fails, a stale row fails, and — because both of those are satisfied by a classifier that has quietly stopped recognising anything — the classifier is driven directly against a sample carrying both shapes. That control earned its place twice during development, rejecting a fixed-line-window exemption that laundered an unrelated call sitting under a legitimate override, then an ordering bug that did the same thing one line closer.

- **`EnsureCanonical` stays, and its meaning changes.** It is no longer detecting a serializer degrading under a publish mode — no input to the writer can produce another name sequence — so it is a post-condition on the writer, which is exactly what a mistyped name or a swapped pair of write statements would trip. Two names earn it on their own: camel casing lowercases a leading **run**, so the spellings are `brickId` (not `brickID`) and `ed25519PublicKey` (not `ed25519publicKey`), and a one-character slip in either changes every signature in that lane. The composition payload gains a post-condition of the same shape; the transition builder deliberately does not, because `StateLogVerifier` answers with a refusal code rather than an exception and compares the hash rather than the payload, so there is nowhere for one to land — its byte pin is the check.
- **Two narrow behaviour changes.** A proposer that supplies the same parameter key twice now raises `CanonicalPayloadException` where the removed intermediate dictionary raised `ArgumentException`: a JSON writer does not reject a duplicate property name, and a payload carrying one describes no single record. The new exception is the one every verification path already catches, so verification refuses (`payload-not-canonical`) instead of throwing into its host. And `CompositionCertificationRecordSigner.Verify` now catches `CanonicalPayloadException` beside `FormatException`, so that lane refuses where the brick lane already refused instead of throwing.

- **Two dead `SixLabors.ImageSharp` references are gone from the consumer graph.** `Ashlar.Tools.Dev` declared `SixLabors.ImageSharp` and `SixLabors.ImageSharp.Drawing`, and nothing in the repository uses either — a grep over every `.cs` file finds no using, no type name, not even a comment, and there is no `#if`-guarded or reflection-by-string use to find. - **A double in the canonical payload is now one chosen decimal form, at one width, on every target — negative zero included.** `WriteNumber(double)` hands the decimal form to whichever formatter the target ships, and the three targets `Ashlar.Certification.Contracts` builds for do not agree. Measured through `BuildPayload` in the devtest container: the shipped `netstandard2.0` asset under Mono 6.12 writes 1/3 as `0.33333333333333331`, 0.007 as `0.0070000000000000001` and 1e-7 as `9.9999999999999995E-08`, where net8.0 and net10.0 (byte-identical to each other on all 18 values probed) write `0.3333333333333333`, `0.007` and `1E-07`. Negative zero diverges in the other direction: net8.0/net10.0 emit `-0`, the ns2.0 asset emits `0`, because Mono's formatter drops the sign of `-0.0` under `"R"`, `"G17"` and the default alike — the sign bit is still observable there (`BitConverter.DoubleToInt64Bits(-0.0)` is correct), only the formatter loses it. These bytes are the message every certification signature is computed over, so a record carrying a non-zero double was signed differently depending on which framework loaded the signer, and a record signed on .NET 10 would not verify against the ns2.0 asset. Since the payload is written rather than serialized, the decimal form is a local decision rather than a serializer behaviour, and it is now made: **17 significant digits on the invariant culture** (`ToString("G17", CultureInfo.InvariantCulture)`), written through `Utf8JsonWriter.WriteRawValue` with input validation left **on**, in both the brick emitter (`CertificationRecordSigning`) and the composition emitter (`CompositionCertificationRecordSigner`). What the width does not fix is the rounding of an exact tie at the 17th significant digit; that residual is stated in full two bullets below.
- **Why G17, and what was rejected on measurement rather than on theory.** Round-trip fidelity is not negotiable for bytes that back a signature, and 17 significant digits is the width at which a binary64 always survives the round trip — a width, not a heuristic, so nothing about it can drift. Every one of the 22 values probed (0, -0, 0.5, 0.25, 1/3, 0.007, ±1e-7, 0.1, `double.Epsilon`, 1e-323, 1e23, 2^53+2, 1e16, 1e21, `MaxValue`, `MinValue`, 1/7, -0.007, 1e-5, 1e-4, 123456789.123456789) formatted G17 to **character-identical** text on net8.0, net10.0 and the ns2.0 asset under Mono, and re-parsed to the identical bit pattern on all three. `"R"` was rejected outright: Mono's `"R"` is not .NET's — 1/3 is `0.33333333333333331` against `0.3333333333333333`, 1e16 is `1E+16` against `10000000000000000`, `double.Epsilon` is `4.94065645841247E-324` (15 significant digits) against `5E-324` — so it would have left the exact divergence it was meant to close, and its meaning changed at .NET Core 3.0 besides. A fixed format was rejected on fidelity: `F17` of `double.Epsilon` is `0.00000000000000000`, the value simply gone, and `F17` of `MaxValue` is a 309-digit integer string; no fixed fractional width spans 10^-324 to 10^308. A hand-written shortest-round-trip ladder (walk G1..G17, take the first precision that re-parses to the same bits) was measured and does work on all three targets — it is the runner-up, and it produces friendlier numbers — but it makes the canonical bytes depend on the **parser** agreeing at every precision as well as the formatter, costs up to 17 format-and-parse cycles per double, and does not actually reproduce .NET's shortest form anyway (`1E+16` for 1e16). One formatter call that only has to agree with itself is the smaller claim — smaller, not empty: at an exact tie it has to agree with the *other* targets' formatters as well, which is the residual the next bullet states.
- **What the chosen width does not fix, measured rather than discovered later.** 17 significant digits is a WIDTH, and a width does not say which way to break a value that falls exactly halfway between two 17-digit decimals — that rounding is still the target formatter's, and the targets break such a tie in opposite directions: Mono 6.12 away from zero, net8.0 and net10.0 to even. Worked case, inside `escapeRate`'s documented 0.0-1.0 range: `0.500003814697265625` (= 0.5 + 2^-18, exactly representable) is written `"escapeRate":0.50000381469726562` on net8.0 and net10.0 and `"escapeRate":0.50000381469726563` on the shipped `netstandard2.0` asset under Mono — same width, different bytes, different signature. Both texts re-parse to the identical bit pattern on their own runtime, so no value is lost; what differs is the bytes, which is the whole of the claim. **No corpus case is such a tie, deliberately** — one would turn `scripts/ns20-canonical-bytes-probe.sh` red over a divergence no producer in this tree can reach (`escapeRate` is survivors over mutants, `durationSeconds` a measured elapsed time) — so `CanonicalDoubleRepresentationTests` pins the value and both known forms instead, and `CertificationRecordSigning.WriteNumberOrNull`, SPEC-006, `CONSUMING.md` and both corpus `_readme`s carry the same qualification. Closing it means deriving the digits from the bit pattern in the emitter rather than asking a formatter for a width: that would move the bytes of every awkward double again, so it is stated here rather than slipped in.
- **Both zeros collapse onto `0`, deliberately, and that is the decision most likely to be "fixed" back.** Forcing `-0` everywhere makes the three writers agree and leaves the system disagreeing: measured under Mono, both `double.Parse("-0")` and `JsonDocument`'s `GetDouble()` on `{"x":-0}` return `+0.0`, while net8.0/net10.0 recover `-0.0` — so a record file written with `-0` yields `+0.0` when an ns2.0 consumer loads it, that consumer re-emits `0`, and the two legs compute different bytes from the same record. Collapsing is stable through emit, read and re-emit on every target, because nothing anywhere has to preserve the sign of a zero. What is given up is the sign bit of zero alone: `-0.0 == 0.0` in IEEE-754, no precision is lost, and no production path can produce `-0.0` in the first place (`escapeRate` is `(double)survivors / total` with `survivors == 0`, which is `+0.0`). The emitter comment says so in those terms.
- **NaN and the infinities are now refused as a canonical-payload fault rather than thrown into the host.** JSON has no number for them, so refusal *is* the canonical answer, and all three targets already refused — but through `ArgumentException` out of `Utf8JsonWriter`, which `CertificationRecordSigning.VerifySignature` does not catch (it catches `FormatException` and `CanonicalPayloadException`) and therefore threw into any caller using it directly; `CertificationTrustVerifier` survived it only through a catch-all and reported `payload-unbuildable`. They are refused explicitly as `CanonicalPayloadException` now, the same vehicle the duplicate-proposer-key and unknown-schema-version refusals use, so `VerifySignature` returns false and the trust verifier reports `payload-not-canonical`. Leaving `skipInputValidation: false` on the `WriteRawValue` call is a second, independent guard: the validating overload re-reads the text as a JSON number on every target, accepting `1E+21` and rejecting `NaN` identically on all three.
- **Migration: this changes the bytes of any record carrying a double that is not exactly representable, and of any record carrying negative zero — and no record in this tree carries either.** Verified rather than assumed. Exactly three sites sign a certification record, and all three reach the signer with `escapeRate` at zero or null: `CertificationGate` and `CompositionCertificationGate` sign only the ADMITTED record, which is reachable only past a rejection on `EscapeRate > 0`, and `LoadRefusalRecord` never assigns it. `durationSeconds` cannot carry a value at all — no production code populates `Attempts`; every assignment of an attempt list is in tests. The three signed records committed to the tree (`samples/certified-brick-reuse/Ashlar.Certified.DamageResolver/certification-record.json`, `spikes/portability/generated/certification-record.json`, `spikes/portability/generated/error-summary-extractor.json`) each carry `"escapeRate": 0` and no attempts, so all three keep their exact bytes and their existing signatures. FAIL records from the gate *do* carry an awkward escape rate (1/3 for one survivor in three) — they are never signed, and the trust verifier reports `record-unsigned` before it ever builds a payload. The invariant therefore holds by the gate's control flow, not by any type constraint, which is exactly why it is pinned in the corpus now rather than trusted.
- **The corpora grow; nothing already pinned moves.** G17 of 0, 0.25 and 0.5 is `0`, `0.25` and `0.5` on all three targets, and those are the only double values any corpus held, so all five `canonical-payloads.golden.json` cases, all four composition cases and all three transition cases keep their exact payload strings, byte lengths and SHA-256s — re-measured, not asserted. Four brick cases and two composition cases are **added**, carrying the values that were not exactly representable: `v1-legacy-awkward-double` (0.1 on the lane with no attempts array), `v2-awkward-doubles` (1/3 as `escapeRate`, 0.007 and 1e-7 as `durationSeconds`), `v2-zero-signs` (`-0` and `+0` in both fields, all emitting `0`), `v2-double-extremes` (`double.Epsilon`, 1e23 — where a shortest form and a 17-digit form are different text — and `double.MaxValue`), plus `composition-awkward-double` and `composition-zero-signs`. `CanonicalDoubleRepresentationTests` pins the reasons a corpus entry cannot state: the form for each value in all three double-bearing fields, the round trip back to the identical bit pattern, the zero collapse, the non-finite refusal on both lanes and through the verifier, and independence from the ambient culture's decimal separator.
- **Measured on every target the change can reach, and one it cannot.** All nine brick payloads are byte-identical and SHA-256-identical on net8.0, net10.0 and the shipped `netstandard2.0` asset executed under Mono 6.12 (`scripts/ns20-canonical-bytes-probe.sh`), and on net10.0 published `PublishTrimmed`/`partial`, `PublishTrimmed`/`full`, the same with reflection re-enabled, and `PublishAot`. **The gap, stated rather than implied:** the ns2.0 leg is the one that diverged, and no workflow runs Mono — `scripts/ns20-canonical-bytes-probe.sh` is still a repeatable local measurement, not CI coverage. After this change the awkward-double cases are checked in CI by xunit on net8.0/net10.0 and by the new trim/AOT lane on net10.0, all of which already agreed; pinning them on the ns2.0 asset stays a local run until a workflow executes it. The parity claim is measured on Mono 6.12.0.182 specifically, which is what `mono:latest` ships; the same asset can be loaded by a .NET Framework host this tree cannot execute.

### Fixed

- **The caller-side half of the LiteDB lost update is closed by removing the shape from three ports, not by asking five callers to remember a precondition.** #602 made every read-modify-write INSIDE a store one transaction and said plainly what it could not reach: a caller that reads through one store method, decides, and writes through another, with the database opened and closed in between. Nine such sites were named. Eight are now closed and one is documented open. **`IMeshTaskRegistry.UpdateAsync(MeshTaskState)` and `IFleetNodeRegistry.RegisterOrUpdateAsync(MeshFleetNodeState)` are gone.** In their place, `UpdateAsync(string taskId, Func<MeshTaskState, MeshTaskState?> transform)` and `RegisterOrMergeAsync(string peerId, Func<MeshFleetNodeState?, MeshFleetNodeState> merge)`: the store reads the document inside its own write transaction, hands it to the caller's function, and writes what comes back, so every precondition is evaluated against the row that is about to be overwritten. Returning `null` from a task transform declines, which surfaces as `MeshTaskUpdateOutcome.PreconditionFailed` and writes nothing. There is no unconditional overload left, so the compiler finds any attempt to write the old SIGNATURE — which matters more here than anywhere else in the repository, because **no automatically triggered workflow compiles `commercial/` at all**. The signature is not the shape, though: `UpdateAsync(task.TaskId, _ => task)` expresses the removed whole-document write through the new port, compiles, and restores the whole measured loss, and the repository's own arrange shim in `Ashlar.Commercial.Tests.Fleet/RegistryArrangeExtensions.cs` is that exact expression. `No_product_call_hands_a_transforming_port_a_discarding_lambda` is what closes it, by requiring the lambda to read its argument; `The_discarding_transform_scan_still_tells_the_two_shapes_apart` drives that classifier. Verified by mutation: adding `_tasks.UpdateAsync(task.TaskId, _ => task, ct)` to product code turns the first fact red.
- **Why a transform and not an `expectedLeaseToken` parameter, measured rather than argued.** Three shapes of the same operation, in the Linux devtest container (net10.0, LiteDB 5.0.21, `Connection=Shared`), 8 threads x 50 read-modify-writes to ONE document, counting the surviving counter. Measured on a standalone probe during this change's scoping pass. Today's shape: 400 attempted, **400 reported successful, 87 survived**, zero exceptions — every caller was told it succeeded. Expected-version compare-and-swap inside the write transaction: 86 applied, 314 refused, 0 lost — correct, but it turns 78% of operations into refusals and needs a retry loop at four of the five call sites. Transform applied inside the store's transaction: **400 applied, 400 survived, 0 refusals, no retry loop.** The transform also subsumes CAS, which is the decisive point: a lease token alone is NOT a sufficient precondition here, because three of the eight mesh write sites operate on a task whose `LeaseToken` is null on both sides of the race. Two concurrent placements of one pending task both satisfy "expect null", both mint a GUID, and the second silently overwrites the first — so a lease-token CAS would have left the double-placement bug standing while looking like it had closed it. `MeshTaskPlacementService.PlacementSnapshotStillStands` states the precondition that actually distinguishes them: lease token, status, attempt count and assigned peer together, which is a revision in everything but name and needs no new field and no migration.
- **Five call sites, each now branching on what the store did instead of reporting what it hoped.** All eight product calls previously discarded `UpdateAsync`'s `bool` and returned their own in-memory value as persisted. `MeshTaskExecutionService.ExtendLeaseAsync` and `MigrateForCheckpointAsync` re-check the lease token (and, for migrate, the Assigned/Running guard) inside the transform and return `lease.invalid_token` / `migrate.invalid_status` when it fails. `MeshLeaseSweepBackgroundService` re-checks that the lease is STILL expired against a clock read inside the transaction rather than against one captured before a whole-collection `ListAsync` — its snapshot of the last element was as old as the entire preceding round. `MeshTaskPlacementService` guards all four of its writes, returns `schedule.conflict` when it loses the placement race, and no longer re-reads after the reclaim because the store hands back what it holds. `CommercialFleetEndpoints.PatchMeshTaskStatusAsync` is now a thin mapper over a new `MeshTaskExecutionService.ApplyStatusAsync`, which also makes the derivation reachable from a test without the HTTP host (`Ashlar.Commercial.Tests.Fleet.Host` is in no solution and no lane).
- **Two behaviour changes on `PATCH /api/mesh/tasks/{id}/status`, both deliberate, both security-relevant.** The lease comparison used to be gated on `body.Status is Running or Assigned`, so for **Succeeded, Failed and Pending there was no comparison at all** — and those are exactly the three arms that null `LeaseToken`, `LeaseOwnerPeerId` and `LeaseExpiresUtc`. - **Every LiteDB store now opens Shared, and the ten that did not were losing 90-99% of concurrent writes without throwing.** LiteDB's default `Connection=Direct` takes an exclusive file lock for the **lifetime** of a `LiteDatabase`, and every store method here opens one per call — so two overlapping calls race for the file. - **The rest of LiteDB's cold-`BsonMapper` race is closed, and it was corrupting far more often than it was throwing.** PR #586 removed the one manifestation a call site could spell its way out of — `NotSupportedException` out of `LinqExpressionVisitor.ResolveMember`, which only reached LiteDB through an expression. What it could not remove sits inside LiteDB's own document conversion and collection lookup, where every caller arrives: `InvalidOperationException("Collection was modified")` out of `BsonMapper.SerializeObject` under `Insert` and out of `EntityMapper.get_Id` under `GetCollection<T>`, plus a **fourth site the earlier work never named** — `InvalidCastException` and `InvalidOperationException` out of `BsonMapper.DeserializeObject`, on the READ path, which on net8.0 outnumbered every write-side throw combined. An audit entry, a pipeline run record or a fleet node registration written that way is silently wrong on disk and nothing reports it. **`LiteDbDocumentMapper.EnsureMapped<T>()` builds each document type once, single-threaded, before any concurrent caller can reach it**, called from each store's constructor and from the top of each of its public methods (the constructor alone is not enough: a caller holding a store across a `BsonMapper.Global` swap would first-touch a cold mapper on its next call). **The warm-up round-trips the type — `ToObject(ToDocument(...))`, not `ToDocument` alone** — because serialization and deserialization do not walk the same members. The read path walks the member list again in `BsonMapper.GetTypeCtor`, and it does so for the `EntityMapper` of a *member* type that serializing an empty instance never builds: the `Dictionary<string, string>` on both commercial fleet documents, and `PipelineRunDocument.StageRuns` in the same shape here. Warming with `ToDocument` alone therefore left deserialization a concurrent first touch, and it was the two commercial fleet types — the ones the first after-measurement never covered — that showed it: at the same 60 × 8, 5 of 8 iterations threw, 21 throws in all, every one `InvalidOperationException("Collection was modified")` out of `GetTypeCtor` under `Deserialize`, surfacing from `LiteDbFleetNodeRegistry.ListAsync` and `LiteDbMeshTaskRegistry`. After the round trip, the same 60 × 8 re-measured **with** the commercial pair included: **zero throws and zero short documents** — ten core document races on net8.0 and net10.0, all 480 raced `StageRuns` sub-documents among them, and both commercial fleet types on net8.0, the only framework `Ashlar.Commercial.Fleet.Infrastructure` targets.
- **The gate is one lock for every document type, and that lock is the `BsonMapper` instance.** Both choices are load-bearing. LiteDB 5.0.21's `GetEntityMapper` reads `_entities.TryGetValue` **outside** `lock (_entities)` over a plain `Dictionary`, so two *different* types building at once is an unsynchronised read against a dictionary another thread may be resizing — a per-type lock would leave that open. And `Ashlar.Commercial.Fleet.Infrastructure` owns two more document types while deliberately not referencing `Ashlar.Infrastructure`, which carries Roslyn, Docker.DotNet and LlamaSharp; locking the mapper instance lets its own copy of the gate serialise against the core one without that reference. Verified against the LiteDB 5.0.21 source: it locks only `_entities`, `_cacheName`, `_cacheCtor`, `_stream`, `_header`, `_free` and `_transactions` — never a `BsonMapper` instance and never `this` inside `BsonMapper` — so nothing inside the round trip can contend for it. A round trip rather than `GetEntityMapper` because the latter is nonpublic in 5.0.21, while both halves of the round trip call it and *walk* the member list, so the members are proven enumerable rather than merely allocated. The class's **own** statics — the set of warmed types and the mapper it describes — are guarded by a dedicated private static lock, taken inside the mapper's: a `BsonMapper.Global` swap between two callers' reads would otherwise put them on two different monitors while both mutated that one non-thread-safe `HashSet`, one adding as the other cleared. The gate compares `BsonMapper.Global` by reference and re-warms when it changes: production never assigns it, but the tests that prove this fix do, and a `bool` or a `Lazy<T>` would report those cold types as warm and leave them racing while the suite went green.
- **There are thirteen LiteDB document types, not twelve.** `PipelineStageRunDocument` reaches LiteDB only as an element of `PipelineRunDocument.StageRuns`, so it appears in no `GetCollection<T>` and serializing a run with an empty stage list never touches it. Warming only the parent **looks** like it worked and is not: measured at the same 60 × 8, it still wrote **146–160 of ~480 raced stage sub-documents with fields missing, and on net10.0 without throwing once**. - **`LiteDbDataDecisionAuditLog` could lose buffered audit entries permanently, and did, at scale.** `FlushBuffer` drained its `ConcurrentQueue` into a **thread-local list before opening the database**, and held no lock, so two threads could each be inside it holding a slice of the audit trail on their own stack with two Direct-mode `LiteDatabase` handles open on one file — this store, unlike `LiteDbCopilotTaskStore`, never asked for `Connection=Shared`. Two handles over one set of pages is what produces the throws; because the entries had already left the queue, whichever thread threw out of `col.Insert` unwound through `Append` and out of a **void** `Log*` method, taking its slice with it. Nothing re-queued it, and the caller — `LogSanitization`, `LogClassification`, `LogCopilotTask` — is a fire-and-forget audit call that never expected an exception at all. Measured, 20 trials × 8 threads × 200 appends on one instance and one file with the mapper warmed first so none of it is the race above: **net8.0 32,000 in → 780 persisted, 31,220 lost; net10.0 32,000 in → 1,500 persisted, 30,500 lost; 20 of 20 trials lossy on both**. The drain is not by itself lossy — absent a failure every dequeued entry lands in exactly one list and every list is inserted — it is the **amplifier** that turns any flush-time failure into permanent loss, and the unlocked per-call Direct-mode database is what guarantees the failures. Both halves change: the buffer is now a `List` guarded by a flush gate and **nothing leaves it until its insert has returned**, `GetRecent` holds that same gate across its flush *and* the query that reads what the flush wrote, and the connection adopts `Connection=Shared` exactly as `LiteDbCopilotTaskStore` already does (an explicit caller-supplied `Connection=` still wins). After: **600 in, 600 persisted, no throws**, and entries stranded by a flush that could not open the database arrive on the next one.
- **The audit buffer is now capped at 10,000 entries, and overflow is itself audited.** Keeping entries until their insert succeeds is what stops the loss, but it also means a permanently unwritable database — bad path, full disk, revoked permissions — would grow the buffer without bound. At the ceiling the **oldest** entries go, and as soon as a flush succeeds the log writes an `AuditBufferOverflow` entry recording how many were discarded and why, because an audit log that quietly shortens itself is worse than one carrying a gap it admits to. Ten thousand is far beyond any real backlog: the flush threshold is ten, so reaching the ceiling takes on the order of a thousand consecutive failed flushes. **Still open, deliberately:** the class is not `IDisposable` and has no shutdown hook, so up to nine sub-threshold entries are discarded on a clean shutdown. ### Security

- **A package could forge its own `× REFUSED` row into a green `✓ ADMITTED` one through a field nobody had treated as sender-chosen: its `formatVersion`.** That field is a `required` JSON string whose value is whatever the file says, it has no length cap, and `ExtensionPackaging.TryOpen` compares it **first** — before the seal, before the record signature, before the sealer/admitter binding — then quotes it into the refusal. So the bytes reaching the terminal had been verified by nothing at all. A `formatVersion` of `ashpkg/v1` + CR + an SGR-green counterfeit returns the cursor to column zero and repaints the refusal as an admission **carrying a sealer fingerprint**, which is precisely the one part of a row the sender is not supposed to be able to choose; a trailing SGR 8 conceals the `'; expected 'ashpkg/v1'.` tail that would give it away. Every `pkg` verb was affected — `show`, `import` and `publish` on stderr, and `pull`'s `× REFUSED` row, whose **left** half (the filename) an earlier change escaped while leaving the **right** half (this reason) raw. All six sinks now go through the shared escaper, as does `pull`'s `× REJECTED` row and `import`'s `× REFUSED — …`. Earlier reviews cleared this sink three times because they tested **malformed** JSON, where `System.Text.Json` hex-escapes control bytes into its own syntax-error text; a document that *parses* and carries the escapes inside a string bypasses that entirely. The same escaping now also covers the other sender-chosen text those reasons quote — a package's declared file paths and the signed-claim mismatch messages.
- **Sender-chosen text on a refusal line is now length-bounded as well as escaped** (2,000 characters, then an explicit `… [truncated: N characters, limit 2,000]`). Escaping is one-for-one, so it makes a hostile string safe without making it shorter: with `formatVersion` uncapped under the 16 MiB document ceiling, a sender could still choose how many characters the operator's terminal had to render and scroll the row naming the refused file — and every row before it — out of the scrollback.
- **The mesh serve daemon was a sixth `.ashpkg` read path that never went through the bounded read, and on it the gap was an arbitrary file read.** `GET /mesh/v1/pkg/{file}` and the `GET /mesh/v1/index` listing both gated on `FileInfo.Length` and then handed the path to `Results.File`. A file name is validated against a traversal-free pattern and the resolved path is checked for containment — but `Path.GetFullPath` does not resolve symlinks, so a link planted in the published directory satisfies both while pointing anywhere on the host. Measured against the real serve path: `ln -s /etc/passwd d-secret.ashpkg` returned `/etc/passwd`; `ln -s <a 40 MiB file> linked-big.ashpkg` was advertised at **23 bytes** (the length of its target's *path string*) and served at 41,943,040 — ten times the documented 4 MiB ceiling; and one `GET` on a planted FIFO blocked inside `open(2)` in Kestrel's `SendFileAsync`, which a client disconnect cannot unblock, so 105 concurrent requests (the connection limit is 100) wedged the node until `hello` and `index` stopped answering. Both sites now open through the same primitive the CLI verbs use: it refuses a `LinkTarget` without following it, refuses anything not seekable / not `FILE_TYPE_DISK`, opens without ever blocking, and takes the length **off the opened handle** — so the bytes advertised, the bytes bounded, and the bytes served are the same bytes. A refusal is a 404 and never its reason, since this is the one caller whose output goes to a stranger. Serving is still opt-in (`ASHLAR_MESH_SERVE_PORT`), but the published directory is not a private staging area: `ASHLAR_MESH_AUTOSHARE` writes admitted packages into it unattended and it is often a synced folder, so "everything offered is already sealed" described what the node *put* there, not what is there. Issue #488. **The primitive moved** from a private type inside `PkgCommand` to `Ashlar.CLI/Packaging/SafePackageRead.cs` — same behaviour, same refusal wording, now findable by the next path that needs it. With this, the read ceiling claim below covers all six paths: `import`, `show`, `publish`, `pull`, the auto-pull daemon's folder pass, and mesh serve.

- **The `.ashpkg` read ceiling is enforced on every path that reads one — all six of them, mesh serve included (see above; that path was missed until #488), and it is a bounded READ rather than a size check.** Before this, only `pkg import` and `pkg show` consulted a ceiling at all — `pkg publish` and `pkg pull` read the file with `File.ReadAllText` and no bound — and the ceiling they did consult was `FileInfo.Length`, which is not a ceiling: it reports **0** for a FIFO, a Unix socket, and a character device such as `/dev/zero`, and for a **symlink** it reports the length of the target's *path string*, so `ln -s <a 400 MiB file> x.ashpkg` measured about twenty bytes and walked straight past the limit. All four verbs (`import`, `show`, `publish`, `pull`), the mesh auto-pull daemon, and the mesh SERVE endpoints now go through one primitive: a non-blocking open (so a planted FIFO cannot wedge a pull), a refusal for anything that is not a regular file, and a cap enforced on the bytes as they arrive rather than inferred from metadata. **The two bounds are different numbers, and the primitive takes whichever its caller passes.** The four `pkg` verbs pass **16 MiB**, which is `ExtensionPackaging`'s own parse ceiling; the daemon's local folder pass passes **`MeshWire.MaxPackageBytes`, 4 MiB** — the same bound it already applied to a package arriving over HTTP, so a peer cannot make a node buffer more locally than it may over the wire. Either way an oversized or endless file is a refused row in milliseconds instead of an `OutOfMemoryException` or a permanent hang. **Breaking:** a `.ashpkg` larger than 16 MiB that `publish` or `pull` previously accepted is now refused, exit 65. The daemon's 4 MiB is unchanged in value; what changed is that it is now enforced during the read and inside the per-file guard, where the `FileInfo.Length` check it replaces sat outside and took the whole unattended pass down with it.
- **A symlinked `.ashpkg` is refused outright** — fail-closed, and **breaking** for anyone who links packages into a mesh store. The link is not followed, because following it *is* the bypass. The refusal names the way out: point the path argument or `--from` at the directory the package really lives in, or copy the file into the store rather than linking it. This applies to the `.ashpkg` **file** only — a store **directory** that is itself a symlink still works.
- **One planted file can no longer deny every package behind it in a `pkg pull`.** A mesh store is a plain synced directory, so anyone who can write to the share can drop a file into it. Every per-row failure — the read, the gate submission (which sat outside the guard and still aborted the whole pass, e.g. when the receiving project's `.ashlar` cannot be created), and the row rendering — is now a `REFUSED` row that increments the counter and lets the pass continue. A refusal never becomes a silent skip: the pass still exits 65 and the summary names the count. A cancelled pass still cancels.
- **Sender-chosen text in every `.ashpkg` read refusal is escaped before it reaches the terminal.** Two parts of those lines are chosen by whoever wrote to the share and not by the operator: the **filename** — which is also what a `× REFUSED` row falls back to when the package did not parse and there is no summary to print — and the **symlink target** quoted inside the refusal, which reaches the operator even when every character they typed was honest (`pkg import store/x.ashpkg`, on a link someone planted). A bare CR, LF, or ANSI/OSC escape in either could repaint the line into a counterfeit `✓ ADMITTED … sealed by <a fingerprint the operator trusts>`, defeating the sealer fingerprint — the one part of a row a sender cannot choose. C0 and C1 controls (including U+009B, a CSI with no ESC in front of it), DEL, and bidi overrides are now replaced with U+FFFD, on every `pkg pull` refusal row and on the `import` / `show` / `publish` refusals written to stderr; a legitimate non-ASCII package name passes through byte-identical. The pre-existing sites that print a **verified** package's summary, `proposedBy`, or a course detail on the success paths are unchanged and tracked in #483; the escaping helper is shared so that issue can reuse it.

### Fixed

- **Two CI lanes that ran nothing now run on every pull request.** A previous change repaired two test filters that matched zero tests — but the *steps* invoking them were `if: github.event_name == 'workflow_dispatch' && …`, and `pull_request` is the only automatic trigger either workflow has, so the vacuous pass simply moved from the filter to the step condition. Application Tier B (the CLI suite, 207 tests, ~20s) and Security Tier C (the package-admission and untrusted-output suites, 61 tests, ~4s) now use the `github.event_name != 'workflow_dispatch' || …` form their sibling tiers already used; every step's condition was evaluated against a `pull_request` context to confirm the selection, and the dispatch tier choices still resolve as before. Security Gate's `paths:` were also widened to the CLI directories Tier C actually asserts on — a correct step condition never fires if no path change starts the workflow. **`TrustCommandTests` now has an automatic runner** as well: it is a `UnitTestBase` suite reachable only through the `UnitTestBridgeTests` theory, one row of which hangs, so a comment declared it un-runnable — but a single row can be selected by narrowing on `DisplayName`, exactly as the composition/mesh gate already does, and it terminates in 453 ms.
- **`ashlar pkg pull --from` no longer mangles a URL into a path and then reports the operator's own store as missing.** `--from` was a `DirectoryInfo`, so System.CommandLine coerced whatever was typed — `file:///srv/mesh`, `http://peer:8080/store`, `ftp://…` — into a directory name that then "does not exist", which reads as the store having vanished rather than as the wrong kind of argument. It is a string now, resolved before use: a **`file://` URL is accepted** and resolves to the directory it names (the shape a sync client or a file manager's "copy location" hands an operator); `http`/`https` is refused with a pointer to `ASHLAR_MESH_PEERS`, which is where HTTP pull actually lives; any other scheme is refused with the scheme named back; and an empty `--from` is a refusal instead of the unhandled exception `new DirectoryInfo("")` threw. A directory whose *name* merely looks like URL syntax (`store%20v1#2`) is still passed through untouched — the scheme test reads the raw token, because on Unix `Uri` parses an ordinary rooted path as an absolute `file:` URI and routing those through `LocalPath` would percent-decode and truncate real store names, losing a live store to fix a cosmetic one.
- **`ashlar doctor --format-json` now emits the JSON report** instead of parsing the global flag and dropping it. `doctor` spells its own switch `--json`; `--format-json` is the CLI-wide flag and is global, so it parsed here and was silently ignored, handing a caller who was piping stdout into a parser eight lines of prose. Both spellings now reach the report that already existed.

### Changed

- **Progress and diagnostic markers moved from stdout to stderr** (`[progress]`, `[complete]`, `[NN%]`). **Breaking for anything that scraped stdout for them.** They were written to the same stream as the `--format-json` document and bracketed it, so `--format-json --verbose` produced output no JSON reader could parse — under exit 0, a green light over a broken pipeline. stdout is now the document; stderr carries the narration, which is what `--format-json`'s own help text already promised.
- **`--format-json` is now refused, loudly, by commands that have no JSON rendering** — `verify`, `policy show`, `policy set` — instead of being accepted and silently ignored. **Breaking:** those invocations now exit 1 with an explanation on stderr where they previously exited 0 and printed prose. The shared helper locates the option by **alias**, never by name: System.CommandLine strips the leading `--` from `Option.Name`, so the `o.Name == "--format-json"` test spelled elsewhere in the tree matches nothing and reports "no JSON asked for" on every invocation. `docker`, `test portable` and `test multi-env` still carry that test and still ignore the flag — deliberately untouched here; the helper exists so they can be moved onto it.

### Security

- Certification verification gains opt-in strictness (`CertificationVerifyOptions`), applied by both `CertificationTrustVerifier.Verify` and `CertificationRecordSigner.Verify`: a **minimum accepted schema version** (SPEC-006 S-5), a require-Ed25519 mode, and trusted-key pinning. Without the floor, the canonical payload lane is selected by the record's own `SchemaVersion` and the legacy lane leaves `Gate`, `GatesPassed`, `Inputs`, `Proposer`, `Attempts` and `Ed25519PublicKey` outside the signed bytes, so a stripped-and-downgraded record can claim to have passed gates it never ran under a recomputed HMAC. Every default reproduces prior behaviour, so this is a control an operator must switch on; see limitations 7 and 8 in `docs/certification-evidence.md`.

- Remote container-execution routes (`/api/execution/*`) are unmapped unless `Ashlar__Execution__ServeRemoteExecution=true` and are behind auth; the API refuses to start on `Lan`/`Tailnet`/`Public` exposure without built-in auth (escape hatch `Ashlar__Security__AllowUnauthenticatedNetworkExposure=true`); no shipped dev keys (#336).
- Session containers run with `--cap-drop ALL`, `--security-opt no-new-privileges`, `--pull never`, an image digest pin, and a read-only rootfs with declared scratch paths; applied containment is attested on the certificate (#337).
- MCP/A2A surfaces: `Enabled=false` defaults, empty allowlists, `ValidateOnStart`, hard refusal under `ASHLAR_DEPLOYMENT_PROFILE=airgapped`, all-verbs auth and per-IP rate limits on `/api/mcp` and `/api/a2a/*` (#268, #266, #269).
