# Changelog

All notable changes to Ashlar are documented in this file.

The format is based on [Keep a Changelog](https://keepachangelog.com/en/1.1.0/), and the project adheres to [Semantic Versioning](https://semver.org/spec/v2.0.0.html). Commit messages follow Conventional Commits by convention (no commitlint hook or workflow enforces it); `scripts/changelog-snippet-for-release.sh` drafts release notes from the commits since the last `v*` tag.

At release time, move the `[Unreleased]` notes under a new `[X.Y.Z] - YYYY-MM-DD` heading, bump `VERSION`, tag `vX.Y.Z`, and publish a GitHub Release.

## [Unreleased]

### Added

- **Product split scaffolds** under `products/` (workstation, cluster, cloud, native) and framework distributed contracts (`ExecutionEnvelope`, `ResultEvidence`, `ITaskScheduler`, `INativeExecutionHost`).
- **`AshlarDeploymentProfile.SecureWorkstation`** — local trust, agents, RAG, and observation without runtime transport. `AirGapped` remains the slim offline profile. Under AirGapped, MCP client, A2A, and MCP server are all refused. Under SecureWorkstation, MCP client and A2A refuse enablement; local MCP server remains allowed.
- **`products-gate`** runs extractable product scaffolds plus `DistributedContractTests`.
- **`Runtime Portability Gate`** (`.github/workflows/runtime-portability-gate.yml` → `scripts/portability/net9-probe.sh`) — the first 9.0.x runtime pin anywhere in CI. `Ashlar.Certification.Contracts` ships `netstandard2.0`, `net8.0` and `net10.0`; a net9.0 consumer has no asset of its own, so NuGet binds it to `lib/net8.0` — an asset every gate had executed on 8.0 and 10.0 and never on 9.0. The probe packs the contracts with the SDK from `global.json`, publishes a net9.0 consumer of the nupkg **outside** the repo (so NuGet's asset selection, not a `ProjectReference`, is what gets measured), asserts that `lib/net8.0` binding from the consumer's `deps.json`, and then **executes** it on a real 9.0.x runtime: the process must be on 9.x (a silent roll-forward onto 10.x would test nothing new), all five golden canonical payloads must be byte-identical (the probe is the third reader of `canonical-payloads.golden.json`, next to the xunit golden test and the ns2.0 probe — one constant, three readers), a v2 record must mint and verify with HMAC **and** Ed25519 (NSec's `net8.0` asset and its libsodium native load on 9.0 — measured, not assumed), and Default/Strict/pinned verdicts plus every tamper code must match what net8.0 and net10.0 return. Execution rather than compilation on purpose: CI had compiled the ns2.0 asset in three places and caught nothing until a probe ran it. **Advisory**: path-filtered (so it cannot be a required context), not `continue-on-error` (a red run is a real runtime regression), weekly schedule because `setup-dotnet` floats the 9.0.x/10.0.x patch. Locally, hosts without a 9.0 runtime split it as `--build-only` then `--run-in-docker` (`mcr.microsoft.com/dotnet/sdk:9.0`).

### Changed

- **Docs** — product-split, operator env-var tables, protocol, licensing, and CI inventory distinguish `AirGapped` from `SecureWorkstation`, drop the `Ashlar.Client` product-consumption overclaim, and document `products-gate` / `DistributedContractTests` ownership.
- **Published pin is 0.1.2.** `ci/published-version` matches nuget.org and GHCR `nexo-cli:0.1.2`. Consumer-template pins follow the pin. The v0.1.2 `release.yml` pack-and-publish job timed out on nuget.org index lag after a successful push; visibility/registration polls now default to 40×15s (and raise a shorter repo-var budget) so the next tag does not fail the same way. nuget.org restore samples pin `System.Text.Encodings.Web` **10.0.11** so they do not NU1605 against the 0.1.2 graph.
- **`OllamaProvider` no longer loads the model manifest in its constructor**; call `InitializeAsync` (or rely on lazy refresh via `ValidateModel`/`CheckHealth`). `ProviderFactory` warm-up is asynchronous and bounded to 5 s (#567).
- **The canonical certification payload is now pinned byte-for-byte, and a degenerate one is an error rather than an input.** Those bytes are the message every certification signature — HMAC and Ed25519, v1 and v2 — is computed over, so they are the whole basis on which a signature written yesterday still verifies today. They were produced by reflection-based `System.Text.Json` and checked by nothing: `ci/cert-gate-assertions.md` listed "v1/v2 record bytes are frozen" as a merge-blocking assertion while only the v1 lane had a byte pin, and v2 — the shape every live minter emits — had none. **Reflection-based serialization does not survive trimming or ahead-of-time publishing**, and under those publish modes the payload can serialize to the empty object `{}` or lose properties with no exception, no warning, and nothing in the calling code able to tell: it hashes whatever it was handed. Measured across the publish matrix, the same source produced correct bytes, a throw, or `{}` depending only on the target framework and trim settings — which is not a property that can be reasoned about, only asserted. `canonical-payloads.golden.json` now pins both lanes fully populated, both lanes minimal, and an escaping case, and `BuildPayload` refuses to return a payload that is not its lane's exact property-name sequence. Degeneracy is defined as shape rather than size on purpose: no ignore policy is configured, so every declared property is emitted for every record whatever its values — a legitimate minimal certificate is 276 bytes carrying all 13 v1 names as nulls — which makes size useless as a signal and the name sequence a value-independent invariant of the payload type. The check re-parses with `JsonDocument`, which is reflection-free and therefore still works in exactly the configurations that break the serializer, and it catches a reordering as well as an emptying: a reorder loses no information but changes the bytes, which would silently invalidate every signature already written. **Signing propagates the refusal** — a crash at mint time is the correct outcome for bytes nobody can vouch for — while **verification refuses without throwing into its host**: `VerifySignature` returns false and `CertificationTrustVerifier` reports a new `payload-not-canonical` failure code (and `payload-unbuildable` when the record's own JSON cannot produce a payload at all), built before the signature comparison and unconditionally, because a comparison over bytes whose shape has not been established is not a result worth reporting. **Cross-target equality is now measured rather than assumed.** `Ashlar.Certification.Contracts` ships `netstandard2.0`, `net8.0` and `net10.0`, and the ns2.0 target exists for external consumers; a target that serialized these bytes even slightly differently would recompute a different message and refuse certificates the others accept. `scripts/ns20-canonical-bytes-probe.sh` builds the shipped ns2.0 asset, publishes a `net472` consumer against it and executes that under Mono, checking the **same** checked-in corpus the xunit golden test reads — one constant, two readers, because two independently typed copies would drift and the equality claim would evaporate with them. All five payloads are byte-identical on net8.0, net10.0 and the ns2.0 asset under Mono 6.12. The corpus restricts doubles to exactly representable values deliberately: decimal formatting of arbitrary doubles is **not** yet identical across those three targets, and a golden corpus should not claim otherwise. The probe is a script, not a CI leg: netstandard2.0 is not a runtime, so there is nothing to run tests "on", and until a workflow calls it this is a repeatable local measurement rather than merge-blocking coverage. **Not yet covered:** other canonical-bytes producers in this tree are not yet pinned or guarded.
- **Every target framework now reaches the same verdict for the same certification record, and a signature a target cannot evaluate is refused rather than skipped.** `Ashlar.Certification.Contracts` ships `netstandard2.0` for external consumers, and that asset has no Ed25519 implementation (NSec ships `lib/net8.0` only). Its `CertificationTrustVerifier` never read `Ed25519Signature`: under options that did not *require* a signature — `Legacy`, or any custom options with `RequireEd25519Signature` false and no pinning — a record carrying an Ed25519 signature that does not verify fell through to the content-hash check and was TRUSTED, while the net8.0 and net10.0 assets refuse the same bytes with `ed25519-signature-invalid`. Measured on the shipped netstandard2.0 asset under Mono against the golden corpus: the two admitted records carrying an Ed25519 placeholder that is not a signature over anything came back TRUSTED under `Legacy` before this change and are refused with the new `ed25519-signature-unverifiable` code after it; the HMAC-only shapes of every admitted record are TRUSTED before and after. The presence test and the key-missing test now sit outside the target-framework fence, so "present" means the same bytes on every target and `ed25519-key-missing` is reported identically; only the evaluation differs, and where it cannot run the record is refused at the same position in the check sequence (after the HMAC, before the content hash), so a multi-fault record reports the same code everywhere. `ed25519-verification-unavailable` keeps its meaning — strictness was requested that this build cannot deliver — and now fires only for an absent signature. **Behaviour change for netstandard2.0 / .NET Framework consumers:** a dual-signed record verified under `Legacy` on that asset was trusted and is now refused; the set of records that asset trusts is a subset of what net8.0 trusts (HMAC-only records), never a contradiction. No in-repo caller is affected: every production caller is net8.0+ and passes `Strict`. `VerifierParityTests` pins the net8.0 side against the same corpus the probe reads, so the subset property is asserted from both sides against one set of bytes.
- **`StateLogVerifier.Verify` gains an overload that takes `CertificationVerifyOptions`; the existing signature is unchanged and still means `Strict`.** The verifier hardcoded `CertificationVerifyOptions.Strict`, and Strict requires an Ed25519 signature — which the `netstandard2.0` asset of `Ashlar.Certification.Contracts` cannot evaluate. On that asset the state-log verifier therefore could never return a trusted verdict (every transition was `behavior-cert-untrusted` with `ed25519-verification-unavailable` inside), with no configuration escape. The new overload places `options` last and non-optional, because the existing overload takes an optional `string? hmacKey` in the slot a nullable options parameter would otherwise occupy and a literal `null` argument must keep meaning "no key"; the existing signature delegates to it with `Strict`, so no caller changes and no default changes. A null options instance is refused (`verify-options-missing`) in the verifier's own refusal convention rather than defaulted — a verifier that was not told how strict to be must not guess. The overload does not widen what the netstandard2.0 asset can trust: a certificate that carries an Ed25519 signature is refused there under every options instance (see the entry above), so only HMAC-only certificates ever verify on it, and the set it trusts stays a subset of what net8.0 trusts. Measured under Mono on the shipped netstandard2.0 assets with `scripts/ns20-canonical-bytes-probe.sh`: a one-transition log bound to an HMAC-only certificate is refused through the existing signature (`behavior-cert-untrusted: ed25519-verification-unavailable`) and trusted through the overload with `Legacy`; the same log bound to a certificate carrying an Ed25519 signature is refused through the overload with `Legacy` (`ed25519-signature-unverifiable`). `AttestedStateLogBindingTests` pins the net8.0 side: the two signatures yield identical results under Strict, Legacy trusts an HMAC-only log Strict refuses, and null options are refused.
- **An unknown certification schema version is now an error on both the signing and the verification paths, not a guess.** `CertificationRecordSigning.BuildPayload` selected the v2 payload lane on `SchemaVersion is not null`, so a record stamped 3, 7 or `int.MaxValue` was serialized in the v2 shape with that number emitted verbatim — and, because `MinimumSchemaVersion` only says "at least this new", cleared the floor of 2 that `Default` and `Strict` apply. Only null (v1) and `TrustLoopSchemaVersion` (2) select a lane now, through one `IsKnownSchemaVersion` used by both paths so they cannot disagree. Signing propagates the refusal as a `CanonicalPayloadException` — the same vehicle a degenerate payload uses, loud at mint time — while every verification path refuses without throwing: `VerifySignature` and `CertificationRecordEd25519.VerifySignature` return false, `CertificationRecordSigner.Verify` returns false (so a stored record carrying such a version no longer loads), and `CertificationTrustVerifier` reports a dedicated `schema-version-unknown` code rather than `payload-not-canonical`, because that code is documented as the serializer degrading under trimming or ahead-of-time publishing (a deployment fault) and an unknown version is a record fault. Precedence is floor first, so an explicit 0 or 1 under `Default` still reports `schema-version-below-floor`. **Byte-neutral for every valid record:** the null and 2 branches are untouched, `canonical-payloads.golden.json` is unchanged, and the golden tests pass against it as-is; measured on the netstandard2.0 asset under Mono, all five payloads are still byte-identical and a record stamped 3 or `int.MaxValue` is refused there with the same code. No in-repo writer mints any version other than null or 2 (`CertificationGate`, `LoadRefusalRecord`, and every test fixture were checked); a record with another version, however it came to be, was previously accepted by a floor and is now refused everywhere. `UnknownSchemaVersionTests` pins every path.
- **The canonical bytes behind every certification signature and every attested state log are now written rather than serialized, so a trimmed or ahead-of-time publish emits the same bytes a plain build does.** The canonical payload is the message every certification signature — HMAC and Ed25519, v1 and v2 — is computed over, and the certified transition entry hash is what `StateLogVerifier` recomputes for every entry in an attested state log. Three producers built them with reflection-based `System.Text.Json`: `CertificationRecordSigning.BuildPayload` (an anonymous type on the v1 lane, a private positional record on v2), `CompositionCertificationRecordSigner.BuildPayload` (a twelve-member anonymous type, live behind `CompositionCertificationGate`), and `CertifiedTransitionBuilder` (a five-member anonymous type). **Reflection-based serialization does not survive trimming or ahead-of-time publishing.** #584 said so and added the shape guard that turns the failure into a refusal, which is the right outcome for bytes nobody can vouch for — but a refusal is still a host that cannot mint or check a certificate. Measured before this change in the devtest container (SDK 10.0.400) on self-contained `linux-x64` publishes that were actually **run**: under `PublishTrimmed` with `TrimMode=partial`, with `TrimMode=full`, and under `PublishAot`, the payload threw `InvalidOperationException` ("Reflection-based serialization has been disabled for this application"); on net10.0 with `TrimMode=full` and `JsonSerializerIsReflectionEnabledByDefault=true` the v1 anonymous type serialized to the empty object and the guard reported it verbatim — `Expected 13 properties [...] in that order; got 0 []`. Under a trimmed publish the payload could serialize to an empty object, and bytes that back a signature must never be silently empty. All four configurations now emit the golden bytes.
- **All three producers write their payload field by field with `Utf8JsonWriter`**, from name constants the shape guard reads as well, so the byte order is the statement order in one method and the canonical form is a property of this repository rather than of whichever `System.Text.Json` build a consumer resolves — `Ashlar.Certification.Contracts` and `Ashlar.Certification.State` ship `netstandard2.0`, `net8.0` and `net10.0`, which are three different serializer builds behind one "canonical bytes" claim. **`Utf8JsonWriter` still does the encoding, deliberately**: compact output; the default JavaScript encoder with its uppercase `\uXXXX` (so `+` in a Base64 hash is escaped and `/` and `=` are not); the `"O"`-format UTC timestamp as a **string**, never the writer's own `DateTimeOffset` overload, which emits `+00:00` and trims trailing fractional zeros; the literal `null` at every level rather than an omitted property; and `WriteNumber(double)`, so each target keeps its own decimal form. Choosing one decimal form here would be a different change and would move signatures already written; the corpora restrict doubles to exactly representable values for that reason.
- **Byte-neutral, and the golden corpus is the acceptance test.** `canonical-payloads.golden.json` is unchanged by this work. All five payloads are byte-identical, byte-length-identical (435 / 276 / 1213 / 391 / 565) and SHA-256-identical: on net8.0 and net10.0 over three consecutive runs each (141 certification tests per run, all green); on the shipped netstandard2.0 asset executed under Mono 6.12; on the .NET 9.0.20 runtime through the packed nupkg bound to `lib/net8.0`; and on net10.0 published `PublishTrimmed`/`TrimMode=partial`, `PublishTrimmed`/`TrimMode=full`, the same with reflection explicitly re-enabled, and `PublishAot` — each self-contained `linux-x64`, each **run**, each with **zero** `IL`/`AOT`/`TRIM` analysis warnings.
- **The two producers that had no byte pin at all now have one, pinned before they were changed.** `composition-payloads.golden.json` (populated, minimal, escaping, mutant-id ordering) and `transition-entry-hashes.golden.json` (genesis, chained, escaping) sit beside the brick corpus in the same shape with the same regeneration ritual, pinning the payload string, its UTF-8 byte length and its SHA-256 — and, for a transition, the Base64 entry hash a caller can observe through the public API. Both were landed against the unchanged implementations first, so the de-reflection had an oracle rather than an opinion. The composition payload's `BuildPayload` and the transition builder's canonical form became `internal` so the pins can see the bytes; going through a signature or a hash instead would report "it moved" rather than which byte moved it. `scripts/ns20-canonical-bytes-probe.sh` gains the transition entry hashes as a fourth check on the ns2.0 asset, and a new `scripts/portability/trim-aot-canonical-bytes-probe.sh` publishes and runs the four trim/AOT configurations above. Both are repeatable local measurements rather than merge-blocking coverage; no workflow calls either. One thing a corpus cannot pin on its own is which comparer orders a sorted sequence, because ids that read like real mutant ids collate the same way under ordinal and culture rules; the composition corpus gains a case whose ids do not, and `CanonicalPayloadEmitterTests` gains the two the brick lane needs — the mutant-id lists and the `kind`-then-`id` input order.
- **`EnsureCanonical` stays, and its meaning changes.** It is no longer detecting a serializer degrading under a publish mode — no input to the writer can produce another name sequence — so it is a post-condition on the writer, which is exactly what a mistyped name or a swapped pair of write statements would trip. Two names earn it on their own: camel casing lowercases a leading **run**, so the spellings are `brickId` (not `brickID`) and `ed25519PublicKey` (not `ed25519publicKey`), and a one-character slip in either changes every signature in that lane. The composition payload gains a post-condition of the same shape; the transition builder deliberately does not, because `StateLogVerifier` answers with a refusal code rather than an exception and compares the hash rather than the payload, so there is nowhere for one to land — its byte pin is the check.
- **Two narrow behaviour changes.** A proposer that supplies the same parameter key twice now raises `CanonicalPayloadException` where the removed intermediate dictionary raised `ArgumentException`: a JSON writer does not reject a duplicate property name, and a payload carrying one describes no single record. The new exception is the one every verification path already catches, so verification refuses (`payload-not-canonical`) instead of throwing into its host. Reaching it needs a custom `IReadOnlyDictionary`; a real `Dictionary` cannot produce it. And `CompositionCertificationRecordSigner.Verify` now catches `CanonicalPayloadException` beside `FormatException`, so that lane refuses where the brick lane already refused instead of throwing.
- **Still not covered.** Two producers still reach the signed v2 payload through a reflective serializer, and this work changes neither. `SessionEnvironmentInputs` computes `CertificationInput.Hash` by serializing the sandbox spec and the attestation reflectively; `CertificationGate.BuildInputs` (`src/Ashlar.Infrastructure/Certification/CertificationGate.cs:380`) does the same for `request.Witness` and hashes the result into the `witness` input, on the live minting path. `CertificationInput` entries are written **inside** the signed v2 payload, so for either of them a trimmed publish would still produce different signed bytes end to end, for that reason rather than this one. `BrickOutputSerializer.ToCanonicalJson` and `WitnessRunner.CanonicalizeObservation` (witness comparison, not signed) are the same shape. None of them is pinned, guarded or changed here.

### Fixed

- **The rest of LiteDB's cold-`BsonMapper` race is closed, and it was corrupting far more often than it was throwing.** PR #586 removed the one manifestation a call site could spell its way out of — `NotSupportedException` out of `LinqExpressionVisitor.ResolveMember`, which only reached LiteDB through an expression. What it could not remove sits inside LiteDB's own document conversion and collection lookup, where every caller arrives: `InvalidOperationException("Collection was modified")` out of `BsonMapper.SerializeObject` under `Insert` and out of `EntityMapper.get_Id` under `GetCollection<T>`, plus a **fourth site the earlier work never named** — `InvalidCastException` and `InvalidOperationException` out of `BsonMapper.DeserializeObject`, on the READ path, which on net8.0 outnumbered every write-side throw combined. Measured on `02bdb969`, 60 rounds × 8 threads per document type, each thread on its own file with `BsonMapper.Global` reset per round: **net8.0 451 throws but 6,357 documents written with fields missing; net10.0 132 throws but 5,655**. The short documents are the damage — the worst samples carry only `[_id]` where the reference write had 6–12 keys, and **the inserts that produced them returned success**. An audit entry, a pipeline run record or a fleet node registration written that way is silently wrong on disk and nothing reports it. **`LiteDbDocumentMapper.EnsureMapped<T>()` builds each document type once, single-threaded, before any concurrent caller can reach it**, called from each store's constructor and from the top of each of its public methods (the constructor alone is not enough: a caller holding a store across a `BsonMapper.Global` swap would first-touch a cold mapper on its next call). **The warm-up round-trips the type — `ToObject(ToDocument(...))`, not `ToDocument` alone** — because serialization and deserialization do not walk the same members. The read path walks the member list again in `BsonMapper.GetTypeCtor`, and it does so for the `EntityMapper` of a *member* type that serializing an empty instance never builds: the `Dictionary<string, string>` on both commercial fleet documents, and `PipelineRunDocument.StageRuns` in the same shape here. Warming with `ToDocument` alone therefore left deserialization a concurrent first touch, and it was the two commercial fleet types — the ones the first after-measurement never covered — that showed it: at the same 60 × 8, 5 of 8 iterations threw, 21 throws in all, every one `InvalidOperationException("Collection was modified")` out of `GetTypeCtor` under `Deserialize`, surfacing from `LiteDbFleetNodeRegistry.ListAsync` and `LiteDbMeshTaskRegistry`. After the round trip, the same 60 × 8 re-measured **with** the commercial pair included: **zero throws and zero short documents** — ten core document races on net8.0 and net10.0, all 480 raced `StageRuns` sub-documents among them, and both commercial fleet types on net8.0, the only framework `Ashlar.Commercial.Fleet.Infrastructure` targets.
- **The gate is one lock for every document type, and that lock is the `BsonMapper` instance.** Both choices are load-bearing. LiteDB 5.0.21's `GetEntityMapper` reads `_entities.TryGetValue` **outside** `lock (_entities)` over a plain `Dictionary`, so two *different* types building at once is an unsynchronised read against a dictionary another thread may be resizing — a per-type lock would leave that open. And `Ashlar.Commercial.Fleet.Infrastructure` owns two more document types while deliberately not referencing `Ashlar.Infrastructure`, which carries Roslyn, Docker.DotNet and LlamaSharp; locking the mapper instance lets its own copy of the gate serialise against the core one without that reference. Verified against the LiteDB 5.0.21 source: it locks only `_entities`, `_cacheName`, `_cacheCtor`, `_stream`, `_header`, `_free` and `_transactions` — never a `BsonMapper` instance and never `this` inside `BsonMapper` — so nothing inside the round trip can contend for it. A round trip rather than `GetEntityMapper` because the latter is nonpublic in 5.0.21, while both halves of the round trip call it and *walk* the member list, so the members are proven enumerable rather than merely allocated. The class's **own** statics — the set of warmed types and the mapper it describes — are guarded by a dedicated private static lock, taken inside the mapper's: a `BsonMapper.Global` swap between two callers' reads would otherwise put them on two different monitors while both mutated that one non-thread-safe `HashSet`, one adding as the other cleared. The gate compares `BsonMapper.Global` by reference and re-warms when it changes: production never assigns it, but the tests that prove this fix do, and a `bool` or a `Lazy<T>` would report those cold types as warm and leave them racing while the suite went green.
- **There are thirteen LiteDB document types, not twelve.** `PipelineStageRunDocument` reaches LiteDB only as an element of `PipelineRunDocument.StageRuns`, so it appears in no `GetCollection<T>` and serializing a run with an empty stage list never touches it. Warming only the parent **looks** like it worked and is not: measured at the same 60 × 8, it still wrote **146–160 of ~480 raced stage sub-documents with fields missing, and on net10.0 without throwing once**. Warming both gives 0 of 480 on both frameworks. The rule is to warm every type LiteDB will serialize, not every type that names a collection — a future document type that gains a nested class or a `List<SomeDoc>` reintroduces the hole.
- **Not a LiteDB upgrade, because there is nothing to upgrade to.** Upstream knows (issue #2536, closed by PR #2538, merged 2024-11-14, which locks `_entities`), but that fix has never shipped in a stable 5.x: **5.0.21 is the newest stable and everything after it is 6.0.0-prerelease**. Moving `Directory.Packages.props` to `6.0.0-prerelease.81` is one line, but it would put NU5104 on `Ashlar.Infrastructure` and `Ashlar.BackgroundAgents` — both on the public package surface — for a prerelease dependency, the exact consequence this file already records for its A2A pin; LiteDB 6 also changes the engine and the on-disk format, and there is no migration path for the twelve existing `.ashlar/state/*.db` stores. The warm-up is also **strictly stronger here**: PR #2538 stops a half-built mapper being handed out, but the build is still the first concurrent touch, while the warm-up removes that touch. Revisit when 6.0.0 goes stable, as its own change with a file-format migration.
- **`LiteDbDataDecisionAuditLog` could lose buffered audit entries permanently, and did, at scale.** `FlushBuffer` drained its `ConcurrentQueue` into a **thread-local list before opening the database**, and held no lock, so two threads could each be inside it holding a slice of the audit trail on their own stack with two Direct-mode `LiteDatabase` handles open on one file — this store, unlike `LiteDbCopilotTaskStore`, never asked for `Connection=Shared`. Two handles over one set of pages is what produces the throws; because the entries had already left the queue, whichever thread threw out of `col.Insert` unwound through `Append` and out of a **void** `Log*` method, taking its slice with it. Nothing re-queued it, and the caller — `LogSanitization`, `LogClassification`, `LogCopilotTask` — is a fire-and-forget audit call that never expected an exception at all. Measured, 20 trials × 8 threads × 200 appends on one instance and one file with the mapper warmed first so none of it is the race above: **net8.0 32,000 in → 780 persisted, 31,220 lost; net10.0 32,000 in → 1,500 persisted, 30,500 lost; 20 of 20 trials lossy on both**. The drain is not by itself lossy — absent a failure every dequeued entry lands in exactly one list and every list is inserted — it is the **amplifier** that turns any flush-time failure into permanent loss, and the unlocked per-call Direct-mode database is what guarantees the failures. Both halves change: the buffer is now a `List` guarded by a flush gate and **nothing leaves it until its insert has returned**, `GetRecent` holds that same gate across its flush *and* the query that reads what the flush wrote, and the connection adopts `Connection=Shared` exactly as `LiteDbCopilotTaskStore` already does (an explicit caller-supplied `Connection=` still wins). After: **600 in, 600 persisted, no throws**, and entries stranded by a flush that could not open the database arrive on the next one.
- **The audit buffer is now capped at 10,000 entries, and overflow is itself audited.** Keeping entries until their insert succeeds is what stops the loss, but it also means a permanently unwritable database — bad path, full disk, revoked permissions — would grow the buffer without bound. At the ceiling the **oldest** entries go, and as soon as a flush succeeds the log writes an `AuditBufferOverflow` entry recording how many were discarded and why, because an audit log that quietly shortens itself is worse than one carrying a gap it admits to. Ten thousand is far beyond any real backlog: the flush threshold is ten, so reaching the ceiling takes on the order of a thousand consecutive failed flushes. **Still open, deliberately:** the class is not `IDisposable` and has no shutdown hook, so up to nine sub-threshold entries are discarded on a clean shutdown. That is a separate change.
- **The two concurrency suites that were supposed to hold this ground both carried escape hatches, and between them those hatches are why the corruption and the loss sat on `master` unnoticed.** They tolerated any exception whose stack passed through LiteDB (`CameFromLiteDb`) — true at the time, not a reason to keep it once the warm-up removes the concurrent first touch — and `LiteDbMapperConcurrencyTests` explicitly declined to look at returned data because the gap "can write a partially serialized document rather than throwing", which was the larger half of the defect. Both assertions now require the error bag to be **empty**, and every racer names its collection so every raced file is reopened **raw** — the non-generic `GetCollection`, never through the type's mapper, which would fill a missing field with a default and report the document intact — and compared against a warm single-threaded reference write whose width is *measured*, not a constant that could drift low and silently stop detecting anything. The pipeline case now saves a run **with** a stage run and a second case walks into the `StageRuns` array, because a run whose array is full of half-serialized elements has the same key count as a whole one. New **`LiteDbDataDecisionAuditLogFlushTests`** races four threads × 150 appends against **one** instance and one file — the shape the log is actually registered in, and the only shape in which two threads can be inside the flush together, which is why the mapper tests, giving each thread its own file, never saw it — plus a case that makes the database unwritable with a directory standing where the file belongs, so a flush fails deterministically on every platform, then removes it and requires every stranded entry on the next flush. - **Local embeddings were reseeded on every process launch, so a persisted RAG index was never comparable to the queries a later process made against it.** Both local embedding generators derived their per-token value from a randomized string hash: `TokenEmbeddingGenerator` seeded its per-token PRNG with `StringComparer.OrdinalIgnoreCase.GetHashCode(token)`, and the MEAI-shaped `TokenHashEmbeddingGenerator` chose its bucket with `token.ToLowerInvariant().GetHashCode()`. .NET randomizes string hashing per process (Marvin, per-process seed), so the "deterministic" both classes' doc comments promised only ever meant "stable until this process exits" — every launch drew a fresh, unrelated vector basis. Measured in the devtest container, five launches of the same binary put the token `wolverine` in buckets 14, 34, 32, 43 and 62, and gave `rag` five entirely different vectors. The visible symptom was a rare CI failure — `KnowledgeBaseIndexerTests.IndexDocumentsAsync_IndexesFile_AndSearchFindsIt` indexed a document, then searched for a word in that document with `minScore` 0.0 and found nothing, because the cosine between two independently-random vectors is itself random and sometimes fell below zero: replaying that exact scenario as 1000 separate process launches produced 999 distinct scores, 3 of them negative. - **Behaviour change for anyone who persisted embeddings.** Vectors already written to a `SqliteVectorStore` database were produced under some earlier process's hash seed. Each store has a test that fails if its guard is removed. **Scope:** this is a *dimension* check, not a staleness check. ### Security

- **A package could forge its own `× REFUSED` row into a green `✓ ADMITTED` one through a field nobody had treated as sender-chosen: its `formatVersion`.** That field is a `required` JSON string whose value is whatever the file says, it has no length cap, and `ExtensionPackaging.TryOpen` compares it **first** — before the seal, before the record signature, before the sealer/admitter binding — then quotes it into the refusal. So the bytes reaching the terminal had been verified by nothing at all. A `formatVersion` of `ashpkg/v1` + CR + an SGR-green counterfeit returns the cursor to column zero and repaints the refusal as an admission **carrying a sealer fingerprint**, which is precisely the one part of a row the sender is not supposed to be able to choose; a trailing SGR 8 conceals the `'; expected 'ashpkg/v1'.` tail that would give it away. Every `pkg` verb was affected — `show`, `import` and `publish` on stderr, and `pull`'s `× REFUSED` row, whose **left** half (the filename) an earlier change escaped while leaving the **right** half (this reason) raw. All six sinks now go through the shared escaper, as does `pull`'s `× REJECTED` row and `import`'s `× REFUSED — …`. Earlier reviews cleared this sink three times because they tested **malformed** JSON, where `System.Text.Json` hex-escapes control bytes into its own syntax-error text; a document that *parses* and carries the escapes inside a string bypasses that entirely. The same escaping now also covers the other sender-chosen text those reasons quote — a package's declared file paths and the signed-claim mismatch messages.
- **Sender-chosen text on a refusal line is now length-bounded as well as escaped** (2,000 characters, then an explicit `… [truncated: N characters, limit 2,000]`). Escaping is one-for-one, so it makes a hostile string safe without making it shorter: with `formatVersion` uncapped under the 16 MiB document ceiling, a sender could still choose how many characters the operator's terminal had to render and scroll the row naming the refused file — and every row before it — out of the scrollback.
- **The mesh serve daemon was a sixth `.ashpkg` read path that never went through the bounded read, and on it the gap was an arbitrary file read.** `GET /mesh/v1/pkg/{file}` and the `GET /mesh/v1/index` listing both gated on `FileInfo.Length` and then handed the path to `Results.File`. A file name is validated against a traversal-free pattern and the resolved path is checked for containment — but `Path.GetFullPath` does not resolve symlinks, so a link planted in the published directory satisfies both while pointing anywhere on the host. Measured against the real serve path: `ln -s /etc/passwd d-secret.ashpkg` returned `/etc/passwd`; `ln -s <a 40 MiB file> linked-big.ashpkg` was advertised at **23 bytes** (the length of its target's *path string*) and served at 41,943,040 — ten times the documented 4 MiB ceiling; and one `GET` on a planted FIFO blocked inside `open(2)` in Kestrel's `SendFileAsync`, which a client disconnect cannot unblock, so 105 concurrent requests (the connection limit is 100) wedged the node until `hello` and `index` stopped answering. Both sites now open through the same primitive the CLI verbs use: it refuses a `LinkTarget` without following it, refuses anything not seekable / not `FILE_TYPE_DISK`, opens without ever blocking, and takes the length **off the opened handle** — so the bytes advertised, the bytes bounded, and the bytes served are the same bytes. A refusal is a 404 and never its reason, since this is the one caller whose output goes to a stranger. Serving is still opt-in (`ASHLAR_MESH_SERVE_PORT`), but the published directory is not a private staging area: `ASHLAR_MESH_AUTOSHARE` writes admitted packages into it unattended and it is often a synced folder, so "everything offered is already sealed" described what the node *put* there, not what is there. Issue #488. **The primitive moved** from a private type inside `PkgCommand` to `Ashlar.CLI/Packaging/SafePackageRead.cs` — same behaviour, same refusal wording, now findable by the next path that needs it. With this, the read ceiling claim below covers all six paths: `import`, `show`, `publish`, `pull`, the auto-pull daemon's folder pass, and mesh serve.

- **The `.ashpkg` read ceiling is enforced on every path that reads one — all six of them, mesh serve included (see above; that path was missed until #488), and it is a bounded READ rather than a size check.** Before this, only `pkg import` and `pkg show` consulted a ceiling at all — `pkg publish` and `pkg pull` read the file with `File.ReadAllText` and no bound — and the ceiling they did consult was `FileInfo.Length`, which is not a ceiling: it reports **0** for a FIFO, a Unix socket, and a character device such as `/dev/zero`, and for a **symlink** it reports the length of the target's *path string*, so `ln -s <a 400 MiB file> x.ashpkg` measured about twenty bytes and walked straight past the limit. All four verbs (`import`, `show`, `publish`, `pull`), the mesh auto-pull daemon, and the mesh SERVE endpoints now go through one primitive: a non-blocking open (so a planted FIFO cannot wedge a pull), a refusal for anything that is not a regular file, and a cap enforced on the bytes as they arrive rather than inferred from metadata. **The two bounds are different numbers, and the primitive takes whichever its caller passes.** The four `pkg` verbs pass **16 MiB**, which is `ExtensionPackaging`'s own parse ceiling; the daemon's local folder pass passes **`MeshWire.MaxPackageBytes`, 4 MiB** — the same bound it already applied to a package arriving over HTTP, so a peer cannot make a node buffer more locally than it may over the wire. Either way an oversized or endless file is a refused row in milliseconds instead of an `OutOfMemoryException` or a permanent hang. **Breaking:** a `.ashpkg` larger than 16 MiB that `publish` or `pull` previously accepted is now refused, exit 65. The daemon's 4 MiB is unchanged in value; what changed is that it is now enforced during the read and inside the per-file guard, where the `FileInfo.Length` check it replaces sat outside and took the whole unattended pass down with it.
- **A symlinked `.ashpkg` is refused outright** — fail-closed, and **breaking** for anyone who links packages into a mesh store. The link is not followed, because following it *is* the bypass. The refusal names the way out: point the path argument or `--from` at the directory the package really lives in, or copy the file into the store rather than linking it. This applies to the `.ashpkg` **file** only — a store **directory** that is itself a symlink still works.
- **One planted file can no longer deny every package behind it in a `pkg pull`.** A mesh store is a plain synced directory, so anyone who can write to the share can drop a file into it. Every per-row failure — the read, the gate submission (which sat outside the guard and still aborted the whole pass, e.g. when the receiving project's `.ashlar` cannot be created), and the row rendering — is now a `REFUSED` row that increments the counter and lets the pass continue. A refusal never becomes a silent skip: the pass still exits 65 and the summary names the count. A cancelled pass still cancels.
- **Sender-chosen text in every `.ashpkg` read refusal is escaped before it reaches the terminal.** Two parts of those lines are chosen by whoever wrote to the share and not by the operator: the **filename** — which is also what a `× REFUSED` row falls back to when the package did not parse and there is no summary to print — and the **symlink target** quoted inside the refusal, which reaches the operator even when every character they typed was honest (`pkg import store/x.ashpkg`, on a link someone planted). A bare CR, LF, or ANSI/OSC escape in either could repaint the line into a counterfeit `✓ ADMITTED … sealed by <a fingerprint the operator trusts>`, defeating the sealer fingerprint — the one part of a row a sender cannot choose. C0 and C1 controls (including U+009B, a CSI with no ESC in front of it), DEL, and bidi overrides are now replaced with U+FFFD, on every `pkg pull` refusal row and on the `import` / `show` / `publish` refusals written to stderr; a legitimate non-ASCII package name passes through byte-identical. The pre-existing sites that print a **verified** package's summary, `proposedBy`, or a course detail on the success paths are unchanged and tracked in #483; the escaping helper is shared so that issue can reuse it.

### Fixed

- **Two CI lanes that ran nothing now run on every pull request.** A previous change repaired two test filters that matched zero tests — but the *steps* invoking them were `if: github.event_name == 'workflow_dispatch' && …`, and `pull_request` is the only automatic trigger either workflow has, so the vacuous pass simply moved from the filter to the step condition. - **`ashlar pkg pull --from` no longer mangles a URL into a path and then reports the operator's own store as missing.** `--from` was a `DirectoryInfo`, so System.CommandLine coerced whatever was typed — `file:///srv/mesh`, `http://peer:8080/store`, `ftp://…` — into a directory name that then "does not exist", which reads as the store having vanished rather than as the wrong kind of argument. A directory whose *name* merely looks like URL syntax (`store%20v1#2`) is still passed through untouched — the scheme test reads the raw token, because on Unix `Uri` parses an ordinary rooted path as an absolute `file:` URI and routing those through `LocalPath` would percent-decode and truncate real store names, losing a live store to fix a cosmetic one.
- **`ashlar doctor --format-json` now emits the JSON report** instead of parsing the global flag and dropping it. `doctor` spells its own switch `--json`; `--format-json` is the CLI-wide flag and is global, so it parsed here and was silently ignored, handing a caller who was piping stdout into a parser eight lines of prose. Both spellings now reach the report that already existed.

### Changed

- **Progress and diagnostic markers moved from stdout to stderr** (`[progress]`, `[complete]`, `[NN%]`). **Breaking for anything that scraped stdout for them.** They were written to the same stream as the `--format-json` document and bracketed it, so `--format-json --verbose` produced output no JSON reader could parse — under exit 0, a green light over a broken pipeline. stdout is now the document; stderr carries the narration, which is what `--format-json`'s own help text already promised.
- **`--format-json` is now refused, loudly, by commands that have no JSON rendering** — `verify`, `policy show`, `policy set` — instead of being accepted and silently ignored. **Breaking:** those invocations now exit 1 with an explanation on stderr where they previously exited 0 and printed prose. The shared helper locates the option by **alias**, never by name: System.CommandLine strips the leading `--` from `Option.Name`, so the `o.Name == "--format-json"` test spelled elsewhere in the tree matches nothing and reports "no JSON asked for" on every invocation. `docker`, `test portable` and `test multi-env` still carry that test and still ignore the flag — deliberately untouched here; the helper exists so they can be moved onto it.

### Added

### Security

- Certification verification gains opt-in strictness (`CertificationVerifyOptions`), applied by both `CertificationTrustVerifier.Verify` and `CertificationRecordSigner.Verify`: a **minimum accepted schema version** (SPEC-006 S-5), a require-Ed25519 mode, and trusted-key pinning. Every default reproduces prior behaviour, so this is a control an operator must switch on; see limitations 7 and 8 in `docs/certification-evidence.md`.

- Remote container-execution routes (`/api/execution/*`) are unmapped unless `Ashlar__Execution__ServeRemoteExecution=true` and are behind auth; the API refuses to start on `Lan`/`Tailnet`/`Public` exposure without built-in auth (escape hatch `Ashlar__Security__AllowUnauthenticatedNetworkExposure=true`); no shipped dev keys (#336).
