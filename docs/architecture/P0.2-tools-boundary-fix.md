# Architecture Fix: P0.2 Tools Boundary Circular Dependency

## Problem

**Architecture Guardian Finding P0.2**: Circular dependency between Infrastructure and Tools layers.

### Before (Circular Dependency)

```
┌──────────────────────────────────────────────────────────────┐
│                      CIRCULAR CYCLE                          │
│                                                              │
│  Ashlar.Infrastructure                                       │
│         │                                                    │
│         ├─► Ashlar.Tools.Assembly ──┐                       │
│         │                            │                       │
│         ├─► Ashlar.Tools.Dev ────────┼──► Ashlar.Core.Application
│         │                            │            ▲          │
│         └────────────────────────────┴────────────┘          │
│                                                              │
└──────────────────────────────────────────────────────────────┘
```

**Violations:**
- `Ashlar.Infrastructure` ProjectReferences `Ashlar.Tools.Assembly` and `Ashlar.Tools.Dev`
- `Ashlar.Tools.Dev` ProjectReferences `Ashlar.Core.Application`
- `Ashlar.Infrastructure` also ProjectReferences `Ashlar.Core.Application`
- Creates cycle: Infrastructure → Tools.Dev → Application ← Infrastructure

**Architectural Issues:**
- Violates acyclic dependency principle
- Breaks hexagonal architecture (outer Infrastructure layer depending on Tools adapters)
- Prevents independent deployment and testing of layers

## Solution

**Approach:** Invert dependencies so Tools depend on Application ports only, and Infrastructure does not reference Tools. Composition happens in the Hosting layer (DIP boundary).

### After (Acyclic)

```
┌──────────────────────────────────────────────────────────────┐
│                      Ashlar.Hosting                          │
│                                                              │
│  ┌───────────────┐        ┌──────────────────┐             │
│  │ Tools.Assembly│        │   Tools.Dev      │             │
│  └───────┬───────┘        └────────┬─────────┘             │
│          │                         │                        │
│          │                         │                        │
│          └──────────┬──────────────┘                        │
│                     │                                       │
│                     ▼                                       │
│          ┌──────────────────────┐                          │
│          │  Infrastructure      │                          │
│          └──────────┬───────────┘                          │
│                     │                                       │
│                     ▼                                       │
│          ┌──────────────────────┐                          │
│          │  Core.Application    │                          │
│          └──────────────────────┘                          │
│                                                             │
└─────────────────────────────────────────────────────────────┘

All depend on:
  Ashlar.Abstractions (ITool interface)
```

**Key Changes:**

1. **Infrastructure Layer (Adapter)**
   - ❌ Removed ProjectReferences to `Ashlar.Tools.Assembly` and `Ashlar.Tools.Dev`
   - ✅ Now depends only on `ITool` abstraction from `Ashlar.Abstractions`
   - `SecurityAnalysisRule` and `CodeQualityRule` receive tools via constructor DI
   - `AgentExecutorAdapter` gets tools from `IServiceProvider.GetServices<ITool>()`

2. **Hosting Layer (DI Composition Root)**
   - ✅ Added ProjectReferences to `Ashlar.Tools.Assembly` and `Ashlar.Tools.Dev`
   - ✅ Registers all tool implementations as `ITool` singletons in Phase 20
   - ✅ Injects tools into analysis rules via factory methods
   - ✅ Composes the dependency graph at the DI boundary

3. **Tools Layer**
   - ✅ Remains unchanged - still depends on `Core.Application` for ports
   - ✅ Now properly isolated as outer-layer adapters

```diff
+ services.AddSingleton<ITool, AssemblyAnalyzeTool>();
+ services.AddSingleton<ITool, AssemblyDecompileTool>();
+ services.AddSingleton<ITool, AssemblySecurityScanTool>();
+ services.AddSingleton<ITool, DotnetTestTool>();

+ services.AddScoped<IAnalysisRule>(sp =>
+ {
+     var logger = sp.GetRequiredService<ILogger<SecurityAnalysisRule>>();

+     return new SecurityAnalysisRule(logger, securityTool);
+ });
```

## Architectural Benefits

1. **Acyclic Dependencies**: No circular references between projects
2. **Hexagonal Architecture**: Clear separation of core (Application) from adapters (Infrastructure, Tools)
3. **Dependency Inversion**: Infrastructure and Tools depend on abstractions (ITool), composed at DI boundary
4. **Independent Testing**: Each layer can be tested in isolation
5. **Maintainability**: Changes to Tools don't require Infrastructure rebuilds
6. **SOLID Compliance**: Follows Single Responsibility and Dependency Inversion principles
