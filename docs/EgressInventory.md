# Egress inventory

This inventory began at master `f1f2cff` (2026-10-04) and is maintained with the SPEC-007 phases. The process audit and explicit-site behavior below reflect PR 4.9. Historical line citations in unchanged descriptions refer to the phase that introduced that description; current paths, member names and machine-checked pins identify the maintained routes.

- **The machine-checked half is `ci/egress-inventory.tsv`.** It pins a count per file and per marker, and `EgressGuardConventionTests` (cert-gate) holds those counts exactly. Every TSV row names IDs from this file. Every `EG-…` id that production code passes to the guard must have a row here.
- **What the controls are.** These are classification-style controls inside the runtime. They are not an accredited cross-domain solution.
- **PR 3 landed in two parts.** 3a shipped the guard and its decision log (`IEgressGuard`, `EgressGuard`, `EgressHttp` and `EgressDecisionLog`, in `src/Ashlar.Abstractions/Security/Egress/`), `AddAshlarEgressGuard` and the logger sink it subscribes (in `src/Ashlar.Infrastructure/Egress/`), this inventory and the convention test, and routed nothing. 3b routes every site that is not `Exempt:` or `Unscanned:`, and the TSV's temporary `Unrouted` reason is gone. HTTP clients go through `EgressHttp` or the factory handler: `AddAshlarEgressGuard` is called after every production `AddHttpClient` but two, the consumer SDK's (`Exempt:ConsumerSdk`) and the commercial Fleet registration, whose project cannot reach `Ashlar.Infrastructure` and which Fleet.Host covers by calling it after `AddAshlar`. MEAI targets go through `EgressGuardChatClient`, the outermost layer of `UseAshlarGovernance`, and the rest through explicit `Evaluate` calls. Every decision goes to the `Ashlar-Egress` EventSource, and to the `Ashlar.Egress` logger wherever a subscription exists. Report decisions use Debug; enforced refusals use Warning (PR 4.7). The **Route** column says how each path is routed, and the route vocabulary below maps each route to its TSV pin. An `Exempt:` route is final.
- **PR 3 was report-only.** Both parts recorded decisions without refusing. PRs 4.7 through 4.9 add refusal behavior; profile defaults remain report until the separate switch in PR 4.11.
- **The mode (PR 4.6 plumbing, PR 4.7 route enforcement).** Every decision now records a `Mode` (`report` or `enforce`), the `ModeBasis` that decided it, `Refused` (`Mode` is `enforce` and `Access` does not allow the egress) and `Ref` (a random 64-bit reference, 16 hex digits, that a refused party may be shown in place of the sequence number). The `Ashlar-Egress` event 1 appends `modeBasis`, `refused` and `ref` after `fault`, and its version goes from 0 to 1. **HTTP and governed MEAI routes act on enforced refusals in PR 4.7.** Explicit `Evaluate` sites act on their decisions in PR 4.9; AirGapped and SecureWorkstation now enforce by default (PR 4.11). The netstandard2.0 asset's synchronous-`Send` refusal (PR 4.2, below) is the runtime's, not the guard's, and holds in every mode.
  - **One resolver.** `EgressEnforcement.ResolveMode(profile, override)` in `src/Ashlar.Abstractions/Security/Egress/`. AirGapped and SecureWorkstation default to `enforce`; Full, Server, Edge and System default to `report` (basis `profile:<profile>`). `enforce` raises every profile. A `report` override is ignored on AirGapped (`override-ignored`), is break-glass on SecureWorkstation (`break-glass`), and is honoured on the other profiles (`override`); any other value, a profile that is not one of the six (basis `profile:unrecognised`), and a fault while resolving the mode (basis `fault`) all fail closed to `enforce`. `EgressGuard.Evaluate` resolves the mode in a step of its own, before the classification, so a fault there cannot leave a placeholder that fails open.
  - **Two bindings.** The process binding is `EgressGuard.ProcessDefault`, which the explicit sites call: it reads the profile once per decision (the profile `AddAshlar` noted, else `ASHLAR_DEPLOYMENT_PROFILE`), resolves the mode from it and records that same value, and takes the override from `ASHLAR_EGRESS_MODE`, **read once per process**, by `AddAshlar` or at the first decision, so a later change to the variable does nothing. `AshlarHostingOptions.EgressMode` can only raise the mode to `enforce`; Ashlar never binds it from `IConfiguration`. A guard built without a profile but with an override of its own takes the stricter of that override and the process's, so it can raise its mode but not lower a process that enforces. The composition binding is the guard `AddAshlar` registers, `new EgressGuard(profile, override)` with the strictest profile noted in the process (so a later `AddAshlar` that resolves Full still composes an AirGapped guard after an `AddAshlar(AirGapped)`), which serves the factory clients and the MEAI targets. `AddAshlar` replaces an `IEgressGuard` descriptor only when its instance is `EgressGuard.ProcessDefault` (the `TryAdd` of an `AddAshlarEgressGuard` that may have run first, in RunPod, the node capability runtime, the model-artifact catalog or MeshLab) or the guard an earlier `AddAshlar` composed into the same service collection, and keeps any other, which is the host's own. So a later `AddAshlar` on the same collection that notes a stricter profile or raises the mode reaches that container's guard. A guard built with a profile never reads the environment, so a guard in a container already built, or composed into another collection, keeps the profile and override it was composed with.
  - **The strictest profile noted wins.** Once `AddAshlar` has noted AirGapped nothing replaces it, and once SecureWorkstation, only AirGapped does, so a second `AddAshlar()` with no profile no longer turns an AirGapped process into Full. Tests restore the noted profile and the mode latch through an internal reset seam, `EgressProcessState`, and `ProcessGlobalEnvironmentConventionTests` treats composing AirGapped or SecureWorkstation, raising the mode, and the seam as process-global writes, and pins every file that names the seam or a member that writes this state outside its rules.
  - **Startup line.** A hosted activator logs one line at Information (`Ashlar.Egress`, event 7302 `EgressMode`) with the mode, its basis, the profile of the guard `AddAshlar` composed and whether that profile was defaulted; a break-glass, ignored override or unrecognised override logs at Warning. A later `AddAshlar` on the same collection replaces the line together with the guard, so the line describes the container's guard whenever that guard is one `AddAshlar` composed. When the host's own `IEgressGuard` is the container's guard (registered before `AddAshlar` or after it), that guard decides and the line does not describe it. A process whose mode is not plain `report` also writes the line to standard error, once, so a host-less CLI verb shows it.
- **Route refusals (SPEC-007 PR 4.7).** HTTP sends and each redirect hop call `ThrowIfRefused` before invoking the inner transport; governed MEAI calls refuse before obtaining a task or stream. `EgressRefusedException` derives directly from `Exception`, carries the full operator `Decision`, and exposes a redacted message with reason, site, family, class and random reference. It is not a network failure. Asynchronous HTTP returns a faulted task; synchronous HTTP and MEAI entry points throw immediately. Existing opaque automatic redirects can only be checked after a response; a refused final destination disposes the response and throws, but cannot undo a body already sent.
  - A throwing or null-returning host guard produces a synthetic `NoDecision` under the process mode: enforcement stops even a normally allowed loopback send; report mode delegates. DI resolution failures retain `ProcessDefault`: throws are counted and logged at Warning, missing registrations at Debug (event 7306 `EgressGuardFallback`). Logging faults and re-entrant publish skips do not bypass enforcement; skipped refusal records are counted separately.
  - Event 7301 `EgressRefused` logs the full operator record at Warning once per site/reason per five-minute window. Event 7305 `EgressRefusalsSuppressed` reports the suppressed count when the window ends, even without further traffic; disposal flushes outstanding counts and releases timers. EventSource event 2 `Refused` carries the full record at Warning; event 1 remains unchanged. Governed MEAI also records `denied` / `egress_refused` with the decision through its invocation auditor, before inner middleware runs. A failing auditor cannot mask the policy refusal.
  - PR 4.8 preserves typed refusals through catch-all handling and fixes remote refusal redaction. PR 4.9 makes explicit sites act on decisions. PR 4.11 enables default enforcement on AirGapped and SecureWorkstation.
- **Host-owned factory exceptions (PR 4.11).** `services.Configure<EgressGuardOptions>(o => o.ReportOnlyClients.Add("host-client"))` works after `AddAshlar` and affects only that named factory client, including its redirect hops. It records `host-opt-out` and logs every configured name at startup. AirGapped ignores the list. Naming an Ashlar-owned client, including the unnamed default, fails host startup. The protected registry is checked against production registrations, including commercial code. Faults remain fail-closed.
- **AirGapped route floor.** HTTP and governed MEAI routes enforce if either their decision or the process profile requires AirGapped enforcement. A host guard cannot lower that floor. On other profiles the host guard's mode is honoured; a throwing or null-returning guard uses the process policy. Calling an explicit-profile guard's `Evaluate` directly remains independent of the environment.
- **Explicit sites and operator exports (PR 4.9).** Explicit sites refuse before sending, writing or launching a child, or follow their documented graceful-degradation path. Named CLI file exports alone carry an internal operator initiator and record report/operator-verb. Publish/share, public export APIs and runtime publishing continue to enforce. A refused native or cloud file export preserves an existing bundle; stale files are removed only after the guard permits replacement.
- **Synchronous `Send` on the netstandard2.0 asset is refused, not evaluated (SPEC-007 PR 4.2).** .NET 5–7 apps resolve the netstandard2.0 asset of `Ashlar.Abstractions`, which is compiled against a `DelegatingHandler` with no `Send` to override, so the guard handler cannot evaluate a synchronous `HttpClient.Send` or `HttpMessageInvoker.Send` there. On that asset `EgressHttp.CreateClient` and `Wrap` put a hop under the guard handler (`SynchronousSendRefusedOnNetstandard20Asset`, an `HttpMessageHandler` that overrides only `SendAsync`), so on a runtime that has a synchronous `Send` (.NET 5 or later) the runtime refuses it with `NotSupportedException`, naming the hop, before anything is sent. No Ashlar code runs on that path, so the refusal is not recorded: the caller gets the exception, and no decision is published, neither for the refused send nor when the client or handler is built. `EgressHttp.CreateDelegatingHandler`, whose inner handler a factory pipeline sets, throws `PlatformNotSupportedException` on such a runtime. Replacing the `InnerHandler` of a `Wrap` handler removes the hop, which the `Wrap` docs forbid. This holds in every mode. `SendAsync` is still evaluated, and a redirect on that path is evaluated again; a synchronous `Send` never reaches the follower. On .NET Framework, classic Mono and Unity, which have no synchronous `Send`, nothing is refused; the only change there is the hop itself, one internal forwarding step under the guard handler, which a walker of `DelegatingHandler.InnerHandler` cannot step through (Known limits, below). No Ashlar source makes a synchronous HTTP `Send`, and every Ashlar host binds the net8.0 or later asset. `docs/SdkCompatibilityPolicy.md` states which asset covers synchronous sends; `EgressHttpNetstandard20TwinTests` (cert-gate) runs the netstandard2.0 build to show it.
- **Redirects are evaluated per hop (SPEC-007 PR 4.3/4.3b).** Ashlar disables automatic redirects on unstarted, credential-free `HttpClientHandler` and `SocketsHttpHandler` primaries and remembers the original setting and limit. Its follower sits directly above the primary, including a composite primary's tail. `EgressHttp` follows only the same origin (scheme, host and port; P2); factory clients follow across origins (P1). On both routes, Ashlar’s follower returns an outside-to-Host or link-local redirect unfollowed and records the attempted destination (owner O2, 2026-10-06), including loopback, `*.localhost`, unix and npipe. HTTPS to HTTP and non-HTTP schemes are not followed. Every followed hop records another decision, even within one origin; `Authorization` is cleared. AirGapped and SecureWorkstation default to enforce; HTTP and redirect routes configured to enforce refuse before the denied hop (PR 4.7). Factory binding restores a removed guard (warning 7303) without warning about the normal logging scope; an unknown-primary warning (7304) is AG/SW-only, once per client/type. An outer EgressHttp wrapper carries P2 on its request even when the pipeline already has a factory P1 follower, without changing another request through the shared factory. Both SNS signing clients call `NeverFollowRedirects` on their existing factory primary; real-host twins pin that behaviour. The helper also marks the named client, so its request flag stops an existing shared follower even when the primary's remembered setting permits redirects; another client's request keeps its own policy. Bedrock's `RuntimeConfig` disables SDK redirects. `MeshAutoPullService` and the default MEAI `OllamaHttpChatClient` already refuse redirects. On netstandard2.0 the walker recognises an existing follower through the synchronous-send hop; synchronous sends still throw before it runs.
- **Known limits of routed enforcement.** The following limits remain even when enforcement is enabled:
  - **The redirect mediator cannot take over every transport.** Credentials, unknown primary types, started primaries and immutable or already-started handler chains retain their own redirect behaviour. The final response's changed origin is decided afterwards and warned, when the body may already have gone; intermediate hops and a return to the original origin are invisible. O2 cannot prevent an inward hop taken inside such a transport. A fresh replacement request loses the decision stamp and can produce a duplicate record; if a handler inside a nested factory pipeline also drops the outer P2 or no-follow request flag, that pipeline retains its inner redirect policy; a rewrite before a mediated primary is decided before that send. P2 and the O2 check compare URI spelling, not DNS resolution, so DNS rebinding and remote names resolving to local addresses remain outside this check. A parent starting concurrently with binding can prevent splicing after its primary was disabled; the resulting chain returns redirects instead of following them. Handler-chain replacement after binding can remove the mediator.
  - **Custom headers follow P1 redirects.** A factory client can forward an API-key header and a 307/308 body to another remote origin. Only `Authorization` is cleared; a raw `EgressHttp` client uses full-origin P2. Host-to-Host and Host-to-remote factory redirects remain P1, and a local service can relay onward. Unknown-primary warning names are remembered for the process lifetime.
  - **Bedrock's host is reconstructed** (EG-MDL-02) from the configured region as `https://bedrock-runtime.<region>.amazonaws.com`, unless the inner client reports an absolute `ChatClientMetadata.ProviderUri`, which since PR 4.1 is recorded instead. The AWS MEAI client (`AWSSDK.Extensions.Bedrock.MEAI` 4.0.101.8) reports none, so the default record is the reconstruction; a cert-gate twin pins that. The AWS SDK's own endpoint resolution is not read: `AWS_ENDPOINT_URL`, `AWS_ENDPOINT_URL_BEDROCK_RUNTIME` and a profile `endpoint_url`, the FIPS and dual-stack flags, and partitions other than `aws` (`cn-*` is `amazonaws.com.cn`). So the recorded host can differ from the one the SDK dials. The record still fails closed: model family, `Internal`, whatever the host.
  - **MEAI guard faults are not recorded.** On the MEAI path a host `IEgressGuard` that throws drops that call's decision, and a guard that cannot be resolved falls back to `EgressGuard.ProcessDefault`; neither fault is counted or logged, where the HTTP handler counts `GuardFaults`. The chat layer also does not activate the Debug logger subscription itself (`Ashlar.AI.Pipeline` cannot reference `Ashlar.Infrastructure`), so its decisions reach the Debug log only once a factory client or the hosted activator has subscribed the logger. The EventSource gets every decision either way.
  - **EG-TEL-01 is decided before the host is built.** Its decision reaches the EventSource before a logger subscription exists. A refusal writes a redacted message to standard error, is logged as a startup warning, and prevents registration of both OTLP exporters (PR 4.9).
  - **One site for several ids.** `ProcessCommandRunner` records `EG-PROC-03` for every docker sandbox, compose and kubectl call (EG-EXE-06/07/08). The shared clients record one site each: `EG-MDL-03` for EG-MDL-04/05/06/08, `EG-XPT-01` for EG-XPT-02 and `EG-XPT-03` for EG-XPT-04/05; the MCP client records `EG-XPT-06` for EG-XPT-07.
  - **Loopback is inside the host boundary only for a service that does not relay.** A loopback or `*.localhost` destination is Host (`SystemHigh`) by design, but a local service can forward what it receives off the host: a loopback OTLP collector, the docker daemon, `kubectl proxy` and a local LLM gateway can all do so, and the Ollama daemon itself relays its cloud models. Ashlar cannot tell which local endpoints relay, so it does not narrow Host to a list of loopback ports; per-endpoint labels wait on the destination table (SPEC-007 open question A). One relay is recognised by name (PR 4.1): a model whose id ends in `-cloud` or `:cloud`, in any case, is recorded as an external model at `https://ollama.com`, on the MEAI route (EG-MDL-01, from the call's model or the inner client's default model) and by `OllamaProvider` (EG-MDL-07, one more decision before the chat is sent). The node capability runtime's Ollama backend (EG-MDL-10), the experimental proposer (EG-MDL-11) and the OpenAI-compatible providers (EG-MDL-03, with `OPENAI_COMPAT_BASE_URL` or `OPENAI_BASE_URL` pointed at a local Ollama's `/v1`) record the daemon's URL whatever the model. The rule matches the model id as written: an alias or copy of a cloud model (`ollama cp gpt-oss:120b-cloud mymodel`), or a model set inside a host's inner pipeline (an options-rewriting layer the outermost guard does not see), is recorded at the daemon. `*.localhost` is trusted by its spelling and is never resolved.
  - **Factory clients record `factory:<client name>`** with the family `http.factory` (a network export), the model calls EG-MDL-09/10/13/14 included.
  - **On the netstandard2.0 asset a walker of only `DelegatingHandler.InnerHandler` still stops at the synchronous-send hop.** The hop is there on every runtime that binds that asset, .NET Framework, classic Mono and Unity included: the `InnerHandler` of an `EgressHttp.Wrap` handler is still the hop, not the caller's handler, and the hop is not a `DelegatingHandler`, so that walker stops and does not see the caller's handler. A walker that also steps through the hop's internal `Inner` continues and sees the redirect handler, then the primary. A synchronous `Send` still throws from the hop before the redirect handler runs, with no decision. Grpc.Net.Client walks `InnerHandler` and, on this asset, stops at the hop. `Ashlar.Transport.Grpc` targets net8.0 and net10.0, where the chain is the guard handler, then the redirect handler (itself a `DelegatingHandler`), then the `HttpClientHandler`, so that walk still finds the `HttpClientHandler`.
  - **Two copies of `Ashlar.Abstractions` in one process darken one `Ashlar-Egress` event source.** A process that loads a second copy (a plugin `AssemblyLoadContext`, for example) has two event sources of that name. .NET will not build an event source's descriptors while another live source has the same name and GUID (`EventSource_EventSourceGuidInUse`, unless `System.Diagnostics.Tracing.EventSource.AllowDuplicateSourceNames` is set), so a copy whose source was not enabled before the other copy's appeared can never be enabled: EventPipe, ETW and `EventListener` consumers see none of its decisions. Each copy's decisions still reach that copy's own `EgressDecisionLog` subscribers. The Debug log subscribes only to the copy that `Ashlar.Infrastructure` binds (`EgressDecisionLoggerSubscription`), so a second copy with no subscriber of its own and a dark event source records its decisions nowhere. Found by the SPEC-007 PR 4.2 twin, whose harness enables the guard's own source before it loads the netstandard2.0 copy.

**Producers (SPEC-007 PR 4.5 / 4.5b).** These changes label decisions. HTTP, model and explicit routes honor opt-in enforcement through PRs 4.7–4.9; profile defaults change separately in PR 4.11.

- **Runner and attribution.** `SelfExtendRunnerAdapter.RunAsync` is the only production subject entry. It enters `agent:<id>` at `SystemHigh` around the cycle, admission and auto-share because its snapshot carries unlabelled persisted state and other agents’ output. A runner declaring a lower floor must observe every input it loads. Work created and started inside the frame inherits it; work captured earlier (a transport pump established at MCP connect time, or provider warm-up) keeps its previous context and can remain `no-subject`. Subject ids are bounded to 256 characters, so suffix-only differences can share a basis. A synchronous tool that leaves a subject frame open can change later attribution; monotone nesting still preserves the label. Other hosts, workflows and services remain `no-subject`; wrapping uninstrumented code in a lower-floor host frame does not make its reads labelled.
- **Every tool call is a read.** An open read decides `SystemHigh` on every flow inside it, for labelled tools too, before and after reporting or completion and until disposal. In-order disposal observes the reported result before restoring the enclosing flow. Work created inside the read keeps its pinned `SystemHigh` frame after disposal; out-of-order or off-flow disposal leaves the originating flow pinned as well. The basis remains the nearest live subject, or `no-subject`. A redirect followed during the tool call stays on that flow and at that label. Scenario B therefore records `SystemHighData`; its web-search site/family distinguish it from C5’s model call.
- **Reports cannot end a read.** A tool must implement `IEgressLabelledTool` and be registered directly in a `CapabilityRegistry` for its report to be accepted. It receives only `ReadReporter.Report`; completion and disposal stay with `ToolCallingAgent`. Unlabelled tools, decorators that do not implement the marker, other toolbox implementations and throwing calls count as `SystemHigh`. `RAGTool` is the sole production implementer, currently registered in no production toolbox. Host implementers remain part of the host’s trusted base. A hit is labelled only if its trimmed spelling matches the pipeline’s canonical names ordinally, ignoring case (including `top-secret`), and the registry returns the canonical primitive belonging to that same name. Custom levels and aliases are `SystemHigh` (O1; C3 remains deferred). No hits and the stores’ private typed unrankable-query refusal report `Public`; any other `ArgumentException` remains unreported, including one that copies the fixed diagnostic and appends data. The serialized refusal still contains the same `Refused` and `Reason` fields.
- **Agent-backed responses are reads.** Every governed target other than `local:` or `cloud:` (trimmed, ignoring case) observes `SystemHigh` on completion, fault, synchronous policy denial, and before each streamed update is delivered. Empty streams and early disposal observe it too. These targets can return another agent’s data until PR 5 carries labels on responses. A host’s own client behind a `local:`/`cloud:` key is part of its trusted base; model responses are not reads. The existing three-argument unkeyed guard constructor retains its behavior.
- **Conventions.** `EgressSubjectProducerConventionTests` pins every production `Enter`/`BeginRead`, its floor and enclosing method, requires a `using` outside an iterator, rejects subject aliases/static imports and labelled-marker aliases, and pins the marker implementers. The production population uses the inventory’s trees and csproj-based test exclusions, including shipped TestKit code. Reflection and delegates remain outside this source tripwire.

**Route vocabulary**

The **Route** column below uses these routes. The last column is the pin `ci/egress-inventory.tsv` holds each one to (`guarded_by` for a guarded site, `unguarded_reason` otherwise), and `EgressGuardConventionTests` checks that the pin's route holds.

| Route | Meaning | TSV pin |
|---|---|---|
| `Handler(factory)` | An `IHttpClientFactory` client. `AddAshlarEgressGuard` puts the guard handler on every factory client through one `ConfigureHttpClientDefaults` call. Every Ashlar member that calls `AddHttpClient` calls it after the registration, in the same block, except the consumer SDK's `AddAshlarClient` (`Exempt:ConsumerSdk`) and the commercial Fleet registration, whose project cannot reach `Ashlar.Infrastructure` (`Upstream:` Fleet.Host). | The registration is http.register `Factory`. ## Adding an outbound path

1. **HTTP.** Register the client with `AddHttpClient` and call `AddAshlarEgressGuard` after the registration, in the same block (`Factory`), or build it with `EgressHttp.CreateClient(family, "EG-…")` or `EgressHttp.Wrap(handler, family, "EG-…")` (`Wrapped`). A member that takes an `HttpClient` parameter must be fed only factory clients (`Factory`), be supplied only from one file that routes its own clients (`Upstream:<file>`), or send the client only after a guard (`Precedes`).
2. **Anything else.** Call `guard.Evaluate(new EgressRequest(family, "EG-…", destination)).ThrowIfRefused()` before the primitive, in the same block or an enclosing one.
3. **Record it.** Add a row to this file and the pins to `ci/egress-inventory.tsv`. `EgressGuardConventionTests` fails until both exist.
