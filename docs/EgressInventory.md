# Egress inventory

This file lists every path by which a request or data leaves an Ashlar process, as found at master `f1f2cff` (2026-10-04). It is the written inventory for SPEC-007 PR 3. PR 3b re-derived every line number that points into a file it edited, from the tree it merged, and SPEC-007 PRs 4.1, 4.6 and 4.10 did the same for the files they edited; every other file cited here is unchanged since `f1f2cff` (or, for `EgressGuard.cs`, since PR 3a added it), so its line numbers still hold.

- **The machine-checked half is `ci/egress-inventory.tsv`.** It pins a count per file and per marker, and `EgressGuardConventionTests` (cert-gate) holds those counts exactly. Every TSV row names IDs from this file. Every `EG-…` id that production code passes to the guard must have a row here.
- **What the controls are.** These are classification-style controls inside the runtime. They are not an accredited cross-domain solution.
- **PR 3 landed in two parts.** 3a shipped the guard and its decision log (`IEgressGuard`, `EgressGuard`, `EgressHttp` and `EgressDecisionLog`, in `src/Ashlar.Abstractions/Security/Egress/`), `AddAshlarEgressGuard` and the logger sink it subscribes (in `src/Ashlar.Infrastructure/Egress/`), this inventory and the convention test, and routed nothing. 3b routes every site that is not `Exempt:` or `Unscanned:`, and the TSV's temporary `Unrouted` reason is gone. HTTP clients go through `EgressHttp` or the factory handler: `AddAshlarEgressGuard` is called after every production `AddHttpClient` but two, the consumer SDK's (`Exempt:ConsumerSdk`) and the commercial Fleet registration, whose project cannot reach `Ashlar.Infrastructure` and which Fleet.Host covers by calling it after `AddAshlar`. MEAI targets go through `EgressGuardChatClient`, the outermost layer of `UseAshlarGovernance`, and the rest through explicit `Evaluate` calls. Every decision goes to the `Ashlar-Egress` EventSource, and to the Debug log under `Ashlar.Egress` wherever a logger subscription exists; the guard refuses nothing. The **Route** column says how each path is routed, and the route vocabulary below maps each route to its TSV pin. An `Exempt:` route is final.
- **What PR 3 does and does not do.** Both parts are report-only: the guard decides and logs each decision, and refuses nothing. PR 4 turns enforcement on per deployment profile, with AirGapped and SecureWorkstation enforcing by default.
- **The mode (PR 4.6: plumbing only; the guard refuses nothing).** Every decision now records a `Mode` (`report` or `enforce`), the `ModeBasis` that decided it, `Refused` (`Mode` is `enforce` and `Access` does not allow the egress) and `Ref` (a random 64-bit reference, 16 hex digits, that a refused party may be shown in place of the sequence number). The `Ashlar-Egress` event 1 appends `modeBasis`, `refused` and `ref` after `fault`, and its version goes from 0 to 1. **No route acts on the mode until PR 4.7**, so an `enforce` record says what would have been refused, not that a send stopped; the opt-in below is not a supported setting until the switch (PR 4.11). The netstandard2.0 asset's synchronous-`Send` refusal (PR 4.2, below) is the runtime's, not the guard's, and holds in every mode.
  - **One resolver.** `EgressEnforcement.ResolveMode(profile, override)` in `src/Ashlar.Abstractions/Security/Egress/`. Every profile defaults to `report` (basis `profile:<profile>`). An override of `report` or `enforce` is honoured on every profile (basis `override`); any other value, a profile that is not one of the six (basis `profile:unrecognised`), and a fault while resolving the mode (basis `fault`) all fail closed to `enforce`. `EgressGuard.Evaluate` resolves the mode in a step of its own, before the classification, so a fault there cannot leave a placeholder that fails open.
  - **Two bindings.** The process binding is `EgressGuard.ProcessDefault`, which the explicit sites call: it reads the profile once per decision (the profile `AddAshlar` noted, else `ASHLAR_DEPLOYMENT_PROFILE`), resolves the mode from it and records that same value, and takes the override from `ASHLAR_EGRESS_MODE`, **read once per process**, by `AddAshlar` or at the first decision, so a later change to the variable does nothing. `AshlarHostingOptions.EgressMode` can only raise the mode to `enforce`; Ashlar never binds it from `IConfiguration`. A guard built without a profile but with an override of its own takes the stricter of that override and the process's, so it can raise its mode but not lower a process that enforces. The composition binding is the guard `AddAshlar` registers, `new EgressGuard(profile, override)` with the strictest profile noted in the process (so a later `AddAshlar` that resolves Full still composes an AirGapped guard after an `AddAshlar(AirGapped)`), which serves the factory clients and the MEAI targets. `AddAshlar` replaces an `IEgressGuard` descriptor only when its instance is `EgressGuard.ProcessDefault` (the `TryAdd` of an `AddAshlarEgressGuard` that may have run first, in RunPod, the node capability runtime, the model-artifact catalog or MeshLab) or the guard an earlier `AddAshlar` composed into the same service collection, and keeps any other, which is the host's own. So a later `AddAshlar` on the same collection that notes a stricter profile or raises the mode reaches that container's guard. A guard built with a profile never reads the environment, so a guard in a container already built, or composed into another collection, keeps the profile and override it was composed with.
  - **The strictest profile noted wins.** Once `AddAshlar` has noted AirGapped nothing replaces it, and once SecureWorkstation, only AirGapped does, so a second `AddAshlar()` with no profile no longer turns an AirGapped process into Full. Tests restore the noted profile and the mode latch through an internal reset seam, `EgressProcessState`, and `ProcessGlobalEnvironmentConventionTests` treats composing AirGapped or SecureWorkstation, raising the mode, and the seam as process-global writes, and pins every file that names the seam or a member that writes this state outside its rules.
  - **Startup line.** A hosted activator logs one line at Information (`Ashlar.Egress`, event 7302 `EgressMode`) with the mode, its basis, the profile of the guard `AddAshlar` composed and whether that profile was defaulted; an unrecognised override logs at Warning. A later `AddAshlar` on the same collection replaces the line together with the guard, so the line describes the container's guard whenever that guard is one `AddAshlar` composed. When the host's own `IEgressGuard` is the container's guard (registered before `AddAshlar` or after it), that guard decides and the line does not describe it. A process whose mode is not plain `report` also writes the line to standard error, once, so a host-less CLI verb shows it.
- **Synchronous `Send` on the netstandard2.0 asset is refused, not evaluated (SPEC-007 PR 4.2).** .NET 5–7 apps resolve the netstandard2.0 asset of `Ashlar.Abstractions`, which is compiled against a `DelegatingHandler` with no `Send` to override, so the guard handler cannot evaluate a synchronous `HttpClient.Send` or `HttpMessageInvoker.Send` there. On that asset `EgressHttp.CreateClient` and `Wrap` put a hop under the guard handler (`SynchronousSendRefusedOnNetstandard20Asset`, an `HttpMessageHandler` that overrides only `SendAsync`), so on a runtime that has a synchronous `Send` (.NET 5 or later) the runtime refuses it with `NotSupportedException`, naming the hop, before anything is sent. No Ashlar code runs on that path, so the refusal is not recorded: the caller gets the exception, and no decision is published, neither for the refused send nor when the client or handler is built. `EgressHttp.CreateDelegatingHandler`, whose inner handler a factory pipeline sets, throws `PlatformNotSupportedException` on such a runtime. Replacing the `InnerHandler` of a `Wrap` handler removes the hop, which the `Wrap` docs forbid. This holds in every mode, and `SendAsync` is still evaluated once. On .NET Framework, classic Mono and Unity, which have no synchronous `Send`, nothing is refused; the only change there is the hop itself, one internal forwarding step under the guard handler, which a walker of `DelegatingHandler.InnerHandler` cannot step through (Known limits, below). No Ashlar source makes a synchronous HTTP `Send`, and every Ashlar host binds the net8.0 or later asset. `docs/SdkCompatibilityPolicy.md` states which asset covers synchronous sends; `EgressHttpNetstandard20TwinTests` (cert-gate) runs the netstandard2.0 build to show it.
- **A second gap PR 4 must close before it enforces: redirects.** The guard evaluates the request each `SendAsync` is given. Redirects that the primary handler follows (`AllowAutoRedirect` is on by default; `MeshAutoPullService.cs:57` turns it off, and since PR 4.1 so does the default MEAI Ollama client, `OllamaHttpChatClient.cs:170`) are not evaluated, because the redirect loop runs below every `DelegatingHandler`. On a 307 or 308 the method and body are re-sent and only `Authorization` is cleared, so a first hop recorded as Host (a loopback URL) can deliver its body to a remote host that no decision names. A redirect between two external hosts leaves the label and the verdict the same; only the recorded host is wrong. Before PR 4 enforces, turn automatic redirects off on the `EgressHttp` handler and on the factory primary handler, and follow redirects, where they are needed, outside the guard so it evaluates each hop.
- **AirGapped and SecureWorkstation hygiene (SPEC-007 PR 4.10; defect 5 by default D35, inbound by owner decision Q6).** These are configuration and routing changes, not guard decisions: the guard still refuses nothing, and it stays the backstop for every path below once 4.11 switches it on.
  - **The profile reaches Infrastructure as a value.** `AddAshlar` registers `ResolvedDeploymentProfile` (`src/Ashlar.Infrastructure/Deployment/ResolvedDeploymentProfile.cs`), an immutable singleton never bound from configuration, built from the strictest profile noted in the process (D5), so a later `AddAshlar` that resolves a weaker profile still registers AirGapped. Infrastructure, the API and mesh serve read that value; none reads `ASHLAR_DEPLOYMENT_PROFILE` or the noted profile itself. A composition that never runs `AddAshlar` has none and behaves as before.
  - **AirGapped routes every job locally** (EG-MDL-09, EG-EXE-03). `NcrCapabilityRouter` keeps a job that a remote reason would send off the node and says so: `AirGapped: remote execution unavailable; running locally (<reason>)` (`NcrCapabilityRouter.cs:104-122`). An explicit `PeerNetworkOnly` throws an explained `InvalidOperationException`, since nothing local satisfies it.
  - **AirGapped never escalates to a cloud model** (EG-MDL-03..06). `AdaptiveProviderFactory` drops `openai` and `azure` from the providers it tries on the LLM and the single-image vision paths, whatever the load policy resolved (`AdaptiveProviderFactory.cs:51-52`, `:72`, `:110`). The bare `ProviderFactory`, used when adaptive load balancing is off, is unchanged: a caller that names `openai` and has `OPENAI_API_KEY` still reaches it, and the guard is the backstop.
  - **Four AirGapped boot validators** (`src/Ashlar.Hosting/AshlarServiceCollectionExtensions.AirGapped.cs:69-131`), on the `ValidateOnStart` pattern and bound to the options types: a non-empty `BrickHost:RemoteCatalogBaseUrls` (EG-EXE-01/02), `Ashlar:RunPod:EnablePeerNetworkRouting=true` (EG-EXE-03), `Ashlar:MeshLab:WorkerExecutor:Enabled=true` (EG-EXE-05) and `Ashlar:Meai:Bedrock:Enabled=true` (EG-MDL-02) each fail boot under AirGapped with the setting, the reason and the remedy. The first three also fail at the first resolution of their options, in a process that never starts a host; the Bedrock check runs at host start only, because `AddAshlarMeaiPipeline` registers its options as a ready-made instance.
  - **The ollama.com catalog defaults to off on AirGapped** (EG-MDL-13). The default is applied before any binding, so an explicit `Enabled=true` still turns it on.
  - **Inbound is loopback only on AirGapped and SecureWorkstation** (§11). On SecureWorkstation, an enabled MCP server fails boot when the container registered MCP over HTTP (the service `.WithHttpTransport()` registers, `ModelContextProtocol.AspNetCore.StreamableHttpHandler`); stdio still boots (`ValidateAshlarMcpServerOptions.cs:74-81`). On both profiles Ashlar.API refuses to start when a configured Kestrel address is not loopback (`Kestrel:Endpoints:*:Url`, `urls`/`ASPNETCORE_URLS`, and `http_ports`/`https_ports`, which bind every interface; `application/src/Ashlar.API/Program.cs:268-281`), and fails its start when Kestrel bound a non-loopback address anyway, a listener added in code included (`LoopbackListenerVerifier`). Loopback is `localhost`, a loopback address, a Unix socket or a named pipe. The devtest and container images set `ASPNETCORE_HTTP_PORTS=8080`, so the API on those profiles needs a loopback `ASPNETCORE_URLS`. Mesh serve listens on every interface and has no loopback mode, so it refuses to serve on those profiles and binds nothing (EG-MESH-03, `MeshServeService.cs:175-182`); the rest of the daemon keeps running, as for a half-configured TLS setup.
- **Known limits of the routed records.** These are records, not refusals, and none of them changes a request:
  - **Bedrock's host is reconstructed** (EG-MDL-02) from the configured region as `https://bedrock-runtime.<region>.amazonaws.com`, unless the inner client reports an absolute `ChatClientMetadata.ProviderUri`, which since PR 4.1 is recorded instead. The AWS MEAI client (`AWSSDK.Extensions.Bedrock.MEAI` 4.0.101.8) reports none, so the default record is the reconstruction; a cert-gate twin pins that. The AWS SDK's own endpoint resolution is not read: `AWS_ENDPOINT_URL`, `AWS_ENDPOINT_URL_BEDROCK_RUNTIME` and a profile `endpoint_url`, the FIPS and dual-stack flags, and partitions other than `aws` (`cn-*` is `amazonaws.com.cn`). So the recorded host can differ from the one the SDK dials. The record still fails closed: model family, `Internal`, whatever the host.
  - **MEAI guard faults are not recorded.** On the MEAI path a host `IEgressGuard` that throws drops that call's decision, and a guard that cannot be resolved falls back to `EgressGuard.ProcessDefault`; neither fault is counted or logged, where the HTTP handler counts `GuardFaults`. The chat layer also does not activate the Debug logger subscription itself (`Ashlar.AI.Pipeline` cannot reference `Ashlar.Infrastructure`), so its decisions reach the Debug log only once a factory client or the hosted activator has subscribed the logger. The EventSource gets every decision either way.
  - **EG-TEL-01 reaches the EventSource only.** It is decided in `Program.cs` before `builder.Build()`, when no logger subscription exists yet, so the API host does not write it to the Debug log.
  - **One site for several ids.** `ProcessCommandRunner` records `EG-PROC-03` for every docker sandbox, compose and kubectl call (EG-EXE-06/07/08). The shared clients record one site each: `EG-MDL-03` for EG-MDL-04/05/06/08, `EG-XPT-01` for EG-XPT-02 and `EG-XPT-03` for EG-XPT-04/05; the MCP client records `EG-XPT-06` for EG-XPT-07.
  - **Loopback is inside the host boundary only for a service that does not relay.** A loopback or `*.localhost` destination is Host (`SystemHigh`) by design, but a local service can forward what it receives off the host: a loopback OTLP collector, the docker daemon, `kubectl proxy` and a local LLM gateway can all do so, and the Ollama daemon itself relays its cloud models. Ashlar cannot tell which local endpoints relay, so it does not narrow Host to a list of loopback ports; per-endpoint labels wait on the destination table (SPEC-007 open question A). One relay is recognised by name (PR 4.1): a model whose id ends in `-cloud` or `:cloud`, in any case, is recorded as an external model at `https://ollama.com`, on the MEAI route (EG-MDL-01, from the call's model or the inner client's default model) and by `OllamaProvider` (EG-MDL-07, one more decision before the chat is sent). The node capability runtime's Ollama backend (EG-MDL-10), the experimental proposer (EG-MDL-11) and the OpenAI-compatible providers (EG-MDL-03, with `OPENAI_COMPAT_BASE_URL` or `OPENAI_BASE_URL` pointed at a local Ollama's `/v1`) record the daemon's URL whatever the model. The rule matches the model id as written: an alias or copy of a cloud model (`ollama cp gpt-oss:120b-cloud mymodel`), or a model set inside a host's inner pipeline (an options-rewriting layer the outermost guard does not see), is recorded at the daemon. `*.localhost` is trusted by its spelling and is never resolved.
  - **Factory clients record `factory:<client name>`** with the family `http.factory` (a network export), the model calls EG-MDL-09/10/13/14 included.
  - **On the netstandard2.0 asset a chain walker stops at the synchronous-send hop.** The hop is there on every runtime that binds that asset, .NET Framework, classic Mono and Unity included: the `InnerHandler` of an `EgressHttp.Wrap` handler is the internal hop, not the caller's handler, and the hop is not a `DelegatingHandler`. Code that walks a handler chain only through `DelegatingHandler.InnerHandler` stops at the hop and does not see the caller's handler or its type: for example, Grpc.Net.Client's handler-type detection when code outside this repository builds a `GrpcChannel` over a `Wrap` handler on that asset. Ashlar code that can see the hop's internals steps through its `Inner`. `Ashlar.Transport.Grpc`, which builds its channel over a `Wrap` handler, targets net8.0 and net10.0, and every Ashlar host binds the net8.0 or later asset, which has no hop.
  - **Responses on inbound connections are not mediated until PR 5's `CanRead` at the server seams.** PR 4.10 keeps AirGapped and SecureWorkstation listeners on loopback (above), but what an inbound caller receives (§11) is not decided by the guard; a loopback caller, or a local tunnel to one, still receives it. Not covered by 4.10: the gRPC server host binds `127.0.0.1:5001` by default but honours a configured `urls`, and the A2A server is refused on both profiles by its own validator.
  - **Two copies of `Ashlar.Abstractions` in one process darken one `Ashlar-Egress` event source.** A process that loads a second copy (a plugin `AssemblyLoadContext`, for example) has two event sources of that name. .NET will not build an event source's descriptors while another live source has the same name and GUID (`EventSource_EventSourceGuidInUse`, unless `System.Diagnostics.Tracing.EventSource.AllowDuplicateSourceNames` is set), so a copy whose source was not enabled before the other copy's appeared can never be enabled: EventPipe, ETW and `EventListener` consumers see none of its decisions. Each copy's decisions still reach that copy's own `EgressDecisionLog` subscribers. The Debug log subscribes only to the copy that `Ashlar.Infrastructure` binds (`EgressDecisionLoggerSubscription`), so a second copy with no subscriber of its own and a dark event source records its decisions nowhere. Found by the SPEC-007 PR 4.2 twin, whose harness enables the guard's own source before it loads the netstandard2.0 copy.

**Route vocabulary**

The **Route** column below uses these routes. The last column is the pin `ci/egress-inventory.tsv` holds each one to (`guarded_by` for a guarded site, `unguarded_reason` otherwise), and `EgressGuardConventionTests` checks that the pin's route holds.

|---|---|---|
| `Handler(factory)` | An `IHttpClientFactory` client. `AddAshlarEgressGuard` puts the guard handler on every factory client through one `ConfigureHttpClientDefaults` call. | `Governance` | A MEAI chat target. `EgressGuardChatClient` is the outermost middleware in `UseAshlarGovernance`. | `Governance`, for the four (file, marker) pairs that F5 holds. |

- **AirGapped does not stop HTTP egress today.** It still registers RunPod (EG-MDL-09), the peer executor (EG-EXE-03), federated remote bricks (EG-EXE-01/02) and the ollama.com catalog (EG-MDL-13). The mesh serve, pull and beacon (EG-MESH-03/04/05) read only environment variables. **Since PR 4.10** AirGapped routes jobs locally, the adaptive factory never tries a cloud provider, the opt-ins behind EG-EXE-01/02/03/05 and the Bedrock tier fail boot, the ollama.com catalog defaults to off, and mesh serve refuses to serve on AirGapped and SecureWorkstation; the registrations themselves are unchanged (the DI shape is kept, D35), and mesh pull and the beacon still read only environment variables.
- **SecureWorkstation also registers the workflow webhook client** (EG-HTTP-01).
- **"Air-gapped" means three different things:**
  - `ASHLAR_DEPLOYMENT_PROFILE`;
  - `ASHLAR_AIRGAP`, which only `CloudAvailabilityResolver` reads, and which has no consumer;
  - `IExecutionContext.IsAirGapped`, which callers set. It is never derived from the profile.
- **No call site carries a `SecurityLabel`.** The only destination tiers named in code are the MEAI target-key prefixes (`local:`, `peer:`, `cloud:`).

## Adding an outbound path

1. **HTTP.** Register the client with `AddHttpClient` and call `AddAshlarEgressGuard` after the registration, in the same block (`Factory`), or build it with `EgressHttp.CreateClient(family, "EG-…")` or `EgressHttp.Wrap(handler, family, "EG-…")` (`Wrapped`). A member that takes an `HttpClient` parameter must be fed only factory clients (`Factory`), be supplied only from one file that routes its own clients (`Upstream:<file>`), or send the client only after a guard (`Precedes`).
2. **Anything else.** Call `guard.Evaluate(new EgressRequest(family, "EG-…", destination))` before the primitive, in the same block or an enclosing one.
3. **Record it.** Add a row to this file and the pins to `ci/egress-inventory.tsv`. `EgressGuardConventionTests` fails until both exist.
