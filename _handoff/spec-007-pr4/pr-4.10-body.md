## Summary

SPEC-007 PR 4.10, **AirGapped and SecureWorkstation hygiene**: defect 5 by the design's default D35 (the vision no-escalate included), the options-bound AirGapped boot validators, and inbound connections per the owner's answer to Q6 ("loopback only, no MCP over HTTP"). These are configuration and routing changes on two profiles; the egress guard still refuses nothing, and it stays the backstop for every path once 4.11 switches it on. Every other profile is unchanged, and a twin says so.

- **The profile reaches Infrastructure as a value.** `AddAshlar` registers `Ashlar.Infrastructure.Deployment.ResolvedDeploymentProfile`, an immutable singleton built from **the strictest profile noted in the process** (D5), never bound from configuration. Infrastructure, Ashlar.API and mesh serve read it; none reads `AshlarDeploymentProfileEnvironment.Effective` or `ASHLAR_DEPLOYMENT_PROFILE` (design §2.7). A later `AddAshlar` that resolves a weaker profile, on the same collection or another, still registers AirGapped (carry-in from the 4.6 notes; the later call's module set is still its own, which stays 4.11's).
- **AirGapped routes every job locally** (`NcrCapabilityRouter.ResolveExecutionTarget`). A remote reason (overnight or background, VRAM, compute class, queue depth, a preferred peer) becomes `AirGapped: remote execution unavailable; running locally (<reason>)`. An explicit `PeerNetworkOnly` is refused with an explained `InvalidOperationException`. Before this, RunPod was AirGapped's default remote target with no configuration at all.
- **AirGapped never escalates to a cloud model** (`AdaptiveProviderFactory`). On the LLM path and the single-image vision path, `openai` and `azure` are never tried, whatever the load policy resolved: a local resolve tries only itself (the design's `{ resolved }`), and a cloud resolve falls back to the local providers only. The multi-frame vision path, which tries only the resolved provider, refuses a cloud resolve with `ModelUnavailableException` (integrator decision 2).
- **Four AirGapped boot validators**, on the `ValidateOnStart` pattern and bound to the options types: a non-empty `BrickHost:RemoteCatalogBaseUrls`, `Ashlar:RunPod:EnablePeerNetworkRouting=true`, `Ashlar:MeshLab:WorkerExecutor:Enabled=true` and `Ashlar:Meai:Bedrock:Enabled=true`. Each fails boot with the setting, the reason and the remedy. The first three are `IValidateOptions<T>`, so they also fail at the first resolution of the options, in a process that never starts a host. `AddAshlarMeaiPipeline` registers its options as a ready-made instance the options factory never builds, so the Bedrock check is a start-time validator that reads every registered `IOptions<MeaiPipelineOptions>` instance, **and `AddAshlar` itself refuses a Bedrock tier that is already registered when it composes** (from `Ashlar:Meai:Bedrock:Enabled` in configuration, or by host code before it), so a process that never starts a host, such as the `ashlar` CLI, is refused too (integrator decision 8, from the attack list's item 15). A tier registered after `AddAshlar` returns is refused at start.
- **SecureWorkstation's outbound paths are unchanged.** Defect 5 is scoped to AirGapped (design §2.7): SecureWorkstation still routes an overnight job to RunPod by default, its adaptive factory still escalates, and the four validators do not apply there until the switch (4.11). A twin pins it so this PR cannot be read as doing more.
- **The ollama.com catalog defaults to off on AirGapped.** The default is an `IConfigureOptions` inserted first in the collection, so it runs before every binding: an explicit `Enabled=true` still turns it on (it is a default, design §2.7).
- **MCP over HTTP fails boot on SecureWorkstation** (Q6). `ValidateAshlarMcpServerOptions` refuses an enabled server on SecureWorkstation when the container registered the service `.WithHttpTransport()` registers (`ModelContextProtocol.AspNetCore.StreamableHttpHandler`, queried through `IServiceProviderIsService`). Stdio still boots. When the validator cannot tell (no service provider, or the marker type missing after an SDK change), it assumes HTTP, and the stdio twin goes red before a release does.
- **Ashlar.API binds loopback on AirGapped and SecureWorkstation, or does not start** (Q6). After `Build`, before Kestrel binds anything, the API refuses a configured address that is not loopback: `Kestrel:Endpoints:*:Url`, `urls` (`ASPNETCORE_URLS`, `--urls`) and, while `urls` is unset, `http_ports` / `https_ports`, which bind every interface. A hosted `LoopbackListenerVerifier` then checks what Kestrel actually bound (`IServerAddressesFeature`) and fails the start on a non-loopback address, a listener a host adds in code included. Loopback is `localhost`, a loopback address, a Unix socket or a named pipe.

A genuine bind failure still never takes the daemon down (the class contract). This is the owner's text implemented literally; an earlier draft refused to serve instead, which the coordinator rejected as a third behaviour the owner did not write.
- **Known limit, in SPEC-007's PR 4 status and `docs/EgressInventory.md`:** responses on inbound connections are not mediated until PR 5's `CanRead` at the server seams.

These are classification-style controls inside the runtime. They are not an accredited cross-domain solution.

## Deviations and integrator decisions

1. **Mesh serve implements Q6 literally** (no deviation). Q6 as recorded says "the API's listeners and mesh serve must bind loopback, or boot fails": on AirGapped and SecureWorkstation mesh serve binds `localhost` and keeps serving, the API's Kestrel URLs keep the fail-boot rule, and a genuine bind failure keeps the class contract (never takes the daemon down). An earlier draft refused to serve and kept the daemon up; the coordinator rejected it as a third behaviour the owner did not write, which would have needed a dated decisions-log row. The "armed" log line names the bound address so an operator sees `http://localhost:<port>`.
2. **The adaptive factory drops `openai` and `azure` whatever the load policy resolved** (integrator decision, fail closed). The design names the LLM list becoming `{ resolved }` when `resolved` is local and vision dropping `openai`/`azure`; the done-when says vision never tries them. One rule covers both: on AirGapped those two are never tried, so a cloud resolve (for example `ASHLAR_LOAD_PREFERENCE=server` with `OPENAI_API_KEY` set) falls back to `ollama`/`local`, and the multi-frame path, which the design called "resolved only", refuses a cloud resolve.
3. **`ResolvedDeploymentProfile` is an immutable singleton, not an `IOptions<T>`** (integrator decision). The design says "an options value Hosting registers". A plain singleton with get-only properties cannot be lowered by a `Configure<T>` call, an appsettings file or a command-line argument; `AddAshlar` replaces any earlier registration. **Known limit:** host code that registers its own `ResolvedDeploymentProfile` *after* `AddAshlar` replaces it (last registration wins), as host code can replace any Ashlar service; the egress guard, which reads the process profile, stays the backstop for such a host.
4. **The value is captured at composition time**, like the composed guard (4.6): a container composed as Full before AirGapped was noted keeps Full. A later composition in the same process, on the same or another collection, gets AirGapped.
5. **The PeerNetworkOnly refusal is an `InvalidOperationException` thrown by the router.** `ExecutionTarget` has a private constructor and two cases, so a third "refused" case would break `CapabilityRoutingBrick`'s casts; the router's only failure channel is an exception.
6. **The listener check also has a post-bind half** (`LoopbackListenerVerifier`), beyond the configuration check, so a listener a host adds in code fails the start too; it cannot stop the bind, only the start. The configuration check is conservative: it refuses any configured address that is not loopback, so a non-loopback `urls` that Kestrel would have ignored because `Kestrel:Endpoints` is also configured still refuses the start (an over-refusal with an explained message, never an under-refusal).
7. **Not covered, for the owner or a later PR** (each recorded in `docs/EgressInventory.md` or above): the gRPC server host's and the commercial Fleet.Host's configurable `urls` (both compose `AddAshlar`, so the same pre-bind check and `LoopbackListenerVerifier` could be lifted into a Hosting helper they call; the design names only the API and mesh serve); the mesh discovery multicast listener (and the beacon still announces the serve port mesh serve refuses to open: harmless, recorded); the bare `ProviderFactory`; video; `RunPodBrick` invoked directly as a brick.
8. **A Bedrock tier already registered fails `AddAshlar` itself on AirGapped** (integrator decision, fail closed; attack item 15 and design-gap 3). The design's "`ValidateOnStart` pattern" cannot bind to `MeaiPipelineOptions` (a ready-made instance), and a process that never starts a host, the `ashlar` CLI among them, runs no start-time validator. `AddAshlar` therefore reads the collection it is about to return for an `IOptions<MeaiPipelineOptions>` instance with `Bedrock.Enabled` and throws `InvalidOperationException` with the validator's message. This refuses earlier than the design asked, never later; a tier registered after `AddAshlar` returns is still refused at start, and a host-less composition that registers one after `AddAshlar` is the remaining (narrow) gap. The owner can reverse this to start-time only by deleting one call.
9. **The discovery beacon still announces the serve port** (`MeshDiscoverySettings.ServePort`) on AirGapped and SecureWorkstation, where only this host can reach it. Harmless (a stranger's pull is refused at the TCP layer); recorded in the inventory's known limits rather than changed, since the beacon is EG-MESH-05's and outside Q6's two listeners.
10. **MCP on SecureWorkstation, the edges.** An enabled server with **no** transport registered boots (nothing listens; `AshlarMcpServerServiceCollectionExtensionsTests.Enabled_under_secure_workstation_profile_is_valid_for_local_ide` pins it, unchanged); the attack list would refuse it, but the existing test and the stdio host's shape say otherwise, and the check is on the HTTP marker's *registration*, not on the marker *type* being resolvable (a missing type fails closed). A host that sets `Enabled=false`, keeps `.WithHttpTransport()` and maps `MapMcp` itself bypasses the validator (it returns success when disabled); only the loopback rule stands between that and the network. Recorded, not closed: SecureWorkstation must boot with MCP off while the API registers HTTP unconditionally.
11. **The listener check is exercised by a required check only through a tripwire.** The real Kestrel bind, `StartedAsync` and mesh serve's `ListenAnyIP` run on net10.0 outside cert-gate (`mcp-a2a-gate`, `security-gate` tier C). Cert-gate holds `The_API_and_mesh_serve_call_the_listener_checks`, which reads `Program.cs`, `LoopbackListenerVerifier.cs` and `MeshServeService.cs` and pins the pre-bind check and its refusal after `Build()`, the verifier's registration and throw, and mesh serve's `ListenLocalhost` branch before its single `ListenAnyIP`; mutations `api-prebind-certgate` and `mesh-anyip-certgate` show it going red (attack items 21c and 28).
