## 3. Findings

**F1 (major, records-vs-code).** `docs/EgressInventory.md:27` Known limit "MEAI guard faults are not recorded. On the MEAI path a host `IEgressGuard` that throws drops that call's decision ... neither fault is counted or logged" is stale since 4.7: `EgressGuardChatClient.Decide` calls `EgressGuard.EvaluateForRoute` (`EgressGuardChatClient.cs:209`), which counts the fault (`EgressGuardHandler.RecordGuardFault()`, `EgressGuard.cs:184`) and publishes a NoDecision record (`:185`); `A_throwing_or_null_returning_host_guard_obeys_the_process_mode` (chat rows) pins it. The record understates the shipped behaviour (fail-open wording for a fail-closed path). Fix: delete or rewrite the bullet. Severity by the rule: a Known limit that no longer describes the code (minor on exposure, major as a false record); I rate it major because an operator reading it would believe MEAI host-guard faults are silent.

**F2 (major).** The PR 5 slice (#748) is not wired: `SkillComposition.Decide`/`SubjectClearance` have no production caller, `AshlarHostingOptions.Clearance` has no reader, `ExtensionPackage.HighestLevel` is read by nothing but `Decide` (§2.7). SPEC-007 status row 5 "Implemented in #748", §2.3 "Composition is the read this change wires ... composing the skill is `CanRead`" and the #748 body "composing the skill above the agent's clearance is refused" describe a function no composition path calls. No skill composition is refused anywhere today; nothing in the records says so (the only recorded limit is "Inbound response bodies are not mediated here"). The task's question (a skill composed below its clearance can still read above it at runtime) is moot: composition is not checked either. Fix: record "library only; no caller until PR 5 proper" in the row and §2.3, or wire `Decide` at the packaging/host composition seam with a twin.

**F3 (major).** Design §2.7 "every Ashlar inbound listener binds loopback, or boot fails" is implemented for the API and mesh serve only (the owner Q6 row's literal text); the gRPC server host (`Ashlar.Transport.Grpc.Server.Host/Program.cs`, EG-SRV-04) and Fleet.Host (EG-SRV-05/06) apply no loopback rule on AG/SW (§2.9). The narrowing is queued in the phase-G handoff §7 but recorded in neither SPEC-007 nor the inventory as a Known limit. Exposure: a shipped host that binds `ASPNETCORE_URLS=http://+:<port>` on an AG/SW machine serves agent output / knowledge export on every interface; responses are unmediated until PR 5. Fix: a Known-limit line naming the two hosts (and the A2A server's AG/SW refusal as the contrast), or the same `CollectEndpoints` + verifier wiring in both hosts.

**F4 (minor, records).** SPEC 4.11 bullet: "The SecureWorkstation report break-glass is environment-only, latched and logged at Warning." A host-registered `new EgressGuard("secure-workstation", "report")` yields `(report, break-glass)` decisions on every HTTP/MEAI route with no latch and no Warning (`EgressModeResolutionTests.cs:63`; §2.3; probe P1), and `new EgressGuard("full")` lowers SW routes with no break-glass stamp at all (inventory `:19` records that host guards are honoured outside AG). Host code is trusted, so this is wording: say "the only runtime break-glass is the environment variable; a host guard built with another profile or the report override is the host's own policy and is recorded as such".

**F5 (minor).** O2's source-side test treats link-local as inside the boundary (`InsideHostBoundary(requestUri)` includes `IsLinkLocalHost`, `EgressRedirectHandler.cs:238-239`), so a 307 from `http://169.254.x.x` into `http://127.0.0.1:...` is followed with the POST body by a factory client (probe P3). The decisions-log O2 row lists link-local with the inside set, so the code matches the record; the intent ("a remote peer must not bounce a request, body included, to a local service") is not met for a link-local peer (a cloud metadata service or a LAN neighbour).
