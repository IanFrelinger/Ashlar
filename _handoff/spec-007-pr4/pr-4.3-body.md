## Summary

SPEC-007 PR 4.3 closes the redirect gap, still report-only. Before this, the guard handler decided the request it was handed and the primary handler's own redirect loop ran below every `DelegatingHandler`, so a redirect hop (on 307/308 with method and body) went out to a host no decision named. Now an internal follower, `EgressRedirectHandler`, sits directly above the primary handler of every `EgressHttp` client and handler and of every `IHttpClientFactory` client in a container that runs `AddAshlarEgressGuard` (the host's clients included, owner answer Q5), turns an `HttpClientHandler`'s or `SocketsHttpHandler`'s own `AllowAutoRedirect` off, follows as the runtime would have, and decides each new authority (scheme, host and port) with the guard handler's guard, family and site before the hop is sent (R-a, R-b, R-c; D32; D33: factory clients follow across origins, P1; `EgressHttp` clients return a cross-origin 3xx to the caller, P2). A handler between the guard handler and the primary that rewrites `RequestUri` is decided again. A factory client whose own configuration removed the guard handler gets it back with a Warning. A primary Ashlar cannot change (another type, `Credentials` set, already sent) keeps following on its own and the final authority is decided after the send. Both SNS signing-certificate clients and the Bedrock runtime client never follow. By the owner's decision of 2026-10-06 (O2, taken during this lane), a hop from outside the host boundary into it (loopback, `*.localhost`, `unix`, `npipe`, link-local) is never followed on either route: the hop is recorded and the 3xx returned. Base: master `de41a8ac`.

## Behaviour changes (what stays report-only)

Report-only throughout: the guard refuses nothing; a hop the guard would refuse is decided `Refused = true` before it is sent, and still sent, until PR 4.7. In the CHANGELOG (`### Changed`, which is the release-notes record; there is no release-notes file):
1. **The primary handler no longer follows redirects itself; Ashlar's follower does.** `AllowAutoRedirect` reads `false` on every `HttpClientHandler`/`SocketsHttpHandler` primary of every factory client under `AddAshlarEgressGuard` (every `AddAshlar` container, the host's own clients included) and of every `EgressHttp` client or handler, after it is built. Per-hop semantics are the follower's (runtime parity, with two stated differences: a non-HTTP `Location` is returned instead of failing the send; a primary with `Credentials`, of another type, or already started is left as it is and decided after the send).
2. **`EgressHttp` clients return a cross-origin 3xx** (A2A, MCP, gRPC transports, `ProviderFactory`, the cloud availability probe, the `mesh` and `workflow` CLI verbs, the mesh auto-pull client, `MeshDirector`, the IDE tags fallback), so their API-key headers never follow a cross-origin hop. A same-origin redirect is still followed. Consequence named in the Known limits: a redirecting proxy in front of Ollama now makes `IsProviderAvailable("ollama")` false on the legacy path.
3. **Both SNS signing clients and the Bedrock runtime client never follow.** New public API in `Ashlar.Infrastructure`: `EgressHttpClientBuilderExtensions.NeverFollowRedirects`.
4. **A redirect from outside the host boundary into it is never followed** (owner decision 2026-10-06; SPEC-007 decisions log row): the 3xx is returned on both routes with the attempted hop recorded. Cost: a host client behind a remote that legitimately redirects to a local service gets the 3xx and must follow it itself.
5. A redirect hop or rewrite to another authority is a second decision ("one send, one decision" becomes "one authority, one decision"); a cloning handler costs a duplicate decision, never a missing one.
The opt-in variable is not named (4.6's integrator decision 4; `grep -c ASHLAR_EGRESS_MODE CHANGELOG.md` is 0 before and after).

## Deviations and integrator decisions

1. **The enforcement twin does not stop the hop (design §2.6 "hop 2 refused, the server never sees `/b`").** No route acts on `Refused` until PR 4.7 (`EgressRefusedException`, `Refuses`, `ThrowIfRefused` are 4.7's) and seven records say "no route acts on the mode until PR 4.7". Per the integrator's instruction for this lane, the twin asserts the per-hop decision instead: under `new EgressGuard("full", "enforce")` hop 2 to the remote host is decided `Refused = true`, `Access.Reason = SystemHighData`, **before** the hop is sent (the stub's `DecisionsBefore` and, in the differential, the decision's tick before the server's), and the hop is still sent. Both twins (`Under_an_enforcing_guard_…` in the stub and differential classes) say in their reason strings that 4.7 stops it where the decision is made. The seven "report-only" records are untouched. 4.7's twin list should name both.
2. **netstandard2.0: the hop is kept, not folded into the follower** (handoff carry-in offered both). Folding would rename the type the 4.2 twin, TSV row 43, `docs/EgressInventory.md` and the guard remarks pin, and would reintroduce a decision-shaped member on the synchronous path the owner's 2026-10-06 amendment says has no record. Instead the follower's walker steps through the hop's internal `Inner`; the chain on that asset is `Guard > Hop > Follower > primary`; the 4.1 Known limit is **narrowed, not closed**: external walkers (Grpc.Net.Client over a `Wrap` handler on that asset) still stop at the hop; Ashlar's own walker steps through (`On_the_netstandard20_asset_the_follower_is_found_through_the_hop_and_follows_a_same_origin_redirect`).
3. **Presence check, not `[0]`, for the guard handler re-insert** (design R-c says `AdditionalHandlers[0]`): the factory's own logging-scope handler legitimately sits outside the guard (master remarks), and a host may `Insert(0, …)`; a `[0]` check would re-insert a second guard and double every decision. The existing defaults twins (one decision per send with `AddAshlarEgressGuard` registered first) are the ordering evidence.
4. **A missing note is "never decided"** (design silent): a hedging/retry handler that clones the request drops the `Options`; the follower decides the clone with its own guard, family and site (the same as the guard handler's for a factory client). Cost: a duplicate record for the same authority, and a third for a rewritten one (the guard handler's post-send check on its own note). Fail closed; CHANGELOG and `docs/EgressInventory.md` say so.
5. **A started primary is left as it is** (design: "the flip is inside a try [needs a test]"): the setter throws `InvalidOperationException` once the handler has sent; the follower then never follows for it (`Follows = false`), the primary keeps following on its own, and the final authority is decided after the send. The alternative (refuse to build the client) would break `EgressHttp.CreateClient(inner)` callers that reuse a handler. Pinned in the differential against a real started `SocketsHttpHandler`; Known limit.
6. **A composite primary (`Rewriter { InnerHandler = HttpClientHandler }`) is handled better than the design's "unknown primary" fallback**: `Install` walks to the tail, flips it and splices the follower under the rewriter, so the rewrite is decided before the tail sends; the AG/SW Warning looks at the chain's tail, not the wrapper type.
7. **Relative `RequestUri` below the guard** is one authority of its own, decided once as a `Fault` record (`Destination = unknown`), never an exception from the compare.
8. **Bedrock**: `AllowAutoRedirect = false` on the SDK configuration only (the design's "if AWSSDK.Core exposes the setting": it does, 4.0.100.4). Routing the SDK's HTTP through `EgressHttp` via AWS's `HttpClientFactory` seam (which would retire the "Bedrock's host is reconstructed" Known limit) is a follow-up, not this row.
9. **The inward rule's boundary includes link-local, which a decision does not classify as Host.** The owner's O2 text names "loopback, link-local, `*.localhost`" and "the same classification `EgressDestinations` uses for Host"; `EgressDestinations` classifies loopback, `localhost`/`*.localhost`, `unix` and `npipe` as Host and records a link-local address as a network export. The follower's inward set is the Host classification plus link-local (`EgressDestinations.IsLinkLocalHost`), the conservative reading; the record of a refused link-local hop says `NetworkExport`, as every decision for that address does. The decisions-log row says so.
10. **Cancellation between hops** (critic G3): a caller's token cancelled after hop 1 stops the follower before hop 2 is sent **or decided** (no record for a hop that never left; the intermediate 3xx is disposed); `OperationCanceledException` reaches the caller. The runtime's own follower has no explicit check and fails in the connection pool; the result is the same exception with no send.
11. **Floors and counts moved by one occurrence**: the Bedrock factory now builds its client once over one configuration, so `sdk.client` on `AwsBedrockChatClientFactory.cs` is 2 (was 3), the TSV total is 149 (was 150), measured in the container (`ExaminedOccurrences=149`). Row 64, the floors comment and TSV row 38 say so.
